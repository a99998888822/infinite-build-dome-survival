# 美术一致性审计（2026-09-29）

当前问题主要集中在**跨模块画风、屏幕上的像素密度、组件缩放与视觉层级**。不能简单归结为“图片尺寸不统一”或“全部素材都模糊”。同类图标的文件尺寸其实已经较整齐，但不同种类、不同页面之间没有形成统一的显示规范。

本次仅分析并生成审阅证据，未替换正式素材、修改正式游戏逻辑或真实用户存档。

## 1. 范围与证据

- 盘点 `assets/` 中 258 张 PNG，其中 44 张位于 `player/tobe_handled/`，属于待处理原图；其余 214 张具有 PNG 导入配置。另有 7 张 SVG。本报告不把待处理原图算作当前画面缺陷。

- 使用 Godot 4.7.2 的 GL Compatibility / ANGLE 实际渲染，采集首页、角色选择、战斗、属性抽屉、商店、理财和附魔页面。采样角色、敌人位置与商店数据包含审阅夹具，不代表正常游玩的特定存档。

## 3. 主战斗场景：重点是混搭与明暗层级

### 已有基础

- 玩家战斗单帧 54×54，待机/行走使用 `combat/` 专用稿；两个角色各自最多 16 色、硬透明。
- 普通怪物单帧 86×86，13～15 色；骑士单帧 160×160，16 色；湿地 30 张贴图均为 128×128、4～16 色、硬透明。
- 世界 SubViewport 使用最近邻采样、相对逻辑视口的 1 倍渲染和变换像素对齐，不能继续沿用“战斗角色是高清图缩小所以糊”的旧判断。但逻辑视口仍可能整体缩放到窗口，见第 8 节。

### 当前问题

1. **角色比例与细节语言不同。** 玩家是大头、简化四肢的角色，普通怪物是暗色有机轮廓，骑士采用更接近写实比例的盔甲与密集金属高光。即使都限制为 16 色，也不自动成为同一画风。
2. **环境内部像素颗粒差距大。** 天空原图为 256×16 的低细节色带，湿地遗迹为 128×128 像素稿，中央石台为 1024×575、约 18,150 种可见 RGB 的精细图。实际截图里天空大色块、石台密集砖缝和角色轮廓分别采用了不同颗粒。
3. **石台存在缩采样。** `StoneBrickFloor` 仍使用 0.64 倍缩放，约显示为 655×368；最近邻可避免插值软化，但不保证原图细节、线宽都完整保留。湿地还按可见包围框、景深与随机尺寸缩放，属于有意空间处理，需要另外验收像素稳定性。
4. **明暗层级不均衡。** 石台中心亮度烘焙在源图，中心明亮、外围湿地很暗；深色角色与怪物离开中心后有融入背景的风险。应在中央/边缘、亮地/暗地分别验收轮廓，不宜只检查角色原图。

体型差异本身并不是错误：普通怪与精英应当大小不同。实际待机可见包围框约为玩家 24×51、普通怪 32×53、骑士 80×113，均小于各自画布。以后应分别管理“画布尺寸”“脚底锚点”“实际可见身高”“游戏内显示高度”，不要把 54/86/160 的画布差异直接当作体型失控。

证据：`scripts/core/game_root.gd`、`scenes/battle/battle_root.tscn`、`scripts/battle/battle_scenery_catalog.gd`、`scripts/battle/wetland_backdrop.gd`。

## 4. 属性栏：纹理细节重，显示尺寸又损失细节

- 上下包边源图宽 313 像素，分别约 2,187/2,156 种可见 RGB；皮革拉手为 44×28、408 色；中部木纹只有 22 色。**同一面板内部已经混合了不同材质抽象程度。**
- 当前抽屉宽 320，皮肤左侧让出 28，实际绘制宽为 292。`stats_drawer_skin.gd` 按 `size.x / 313` 绘制，即约 **0.933 倍**。因此不仅不是整像素倍率，还把细致的包边缩小了。
- 上下固定件加中段平铺的结构是合理的，已经避免整张面板纵向硬拉。问题在于贴图风格、基础宽度和显示宽度没有统一。
- 实际截图中包边、链条、皮带很显眼，而正文使用 11px 字、14px 最小行高，直接压在木纹上；“框厚、字小、内容挤”的感受来自视觉重量分配，不只来自 PNG 清晰度。

建议保留模块化拼接，统一边角、木纹和拉手的细节档位；让绘制基准宽度与实际宽度匹配；文字区采用更稳定的低对比底纹和字号/行距。金属材质是否保留应由整体 UI 方向决定，不必先删除所有装饰。

证据：`scripts/ui/battle_hud.gd` 的 `_create_stats_drawer_skin()` / `_ensure_stat_rows()`，`scripts/ui/stats_drawer_skin.gd`。

## 5. 理财界面：需要统一组件，而不是只换一张框

- 主板 `finance_board.png` 是 408×260、30 色；通过 `NinePatchRect` 保持四角，四边边距 16，但中心采用默认拉伸。1152×648 截图中的面板约为 800×520，中心木纹被放大为接近两倍，板缝粗细与属性栏平铺木纹不同。
- 柜台为 128×64、16 色；哥布林为每帧 128×128、16 色，素材本身有较好的共同基础。但绘制时人物另乘 `ACTOR_SCALE=0.60`，还根据可用区域动态适配。人物与柜台不是同一像素倍率，需要按最终显示图检查匹配。
- 实际画面同时出现：细线木板框、厚金属属性框、立体柜台、平面色块按钮、金色选中标签、绿色稀有度卡片。统一成棕绿色不等于组件风格统一。
- 理财购买卡的 icon 只有 36×36，描述字较小；装饰区域和留白较大，信息和物品辨识区较弱。附魔页同一武器又以按钮图、26×26 的标题图等形式出现，视觉规格重复但不一致。
- SVG 不是天然错误；不过放大镜图标使用圆弧和 1.5px 描边，与硬边像素符号要有明确统一方式，不能只靠设置 Nearest。

建议以“主面板、内卡、按钮、标签、槽位、提示框”为一套组件制定边框厚度、内边距、选中态和底纹尺度。底纹宜按设计平铺或分层绘制，九宫格主要负责边角。柜台插画可以保留，但需有独立、稳定的显示规格。

证据：`scripts/ui/finance_popup.gd`、`scripts/ui/finance_ui_style.gd`、`scripts/ui/bank_counter_portrait.gd`、`scripts/ui/preparation_offer_card.gd`。

## 6. 图标：文件大小统一，不等于看起来一样大

| 图标组 | 数量与画布 | 可见 RGB 数 | 当前显示例子 | 主要判断 |
|---|---|---|---|---|
| 遗物 | 90 张，全部 32×32 | 除存钱罐外为 6～17；存钱罐为 100 | 理财 36、背包图标最大宽 44、奖励卡自适应 | 主体体系较一致，先修离群项和跨界面缩放 |
| 武器 | 7 张，全部 64×64 | 12～27 | 武器条最大宽 34、理财 36、附魔标题 26、角色选择 48 | 细节比最终显示需求高，细杆武器容易丢线 |
| 附魔 | 10 张，全部 16×16 | 5～8 | 附魔背包 20×20、槽位图像区高 20 | 简化程度明显高于武器；20/16 为非整数倍率 |

三组图标均为硬透明，没有普遍存在半透明杂边。**不建议直接把全部源文件扩成同一分辨率。** 把 16 放大到 64 不会增加有效细节，把 64 缩成 16 又会损失轮廓。

### 遗物

- 绝大多数使用深色描边、有限色板、简化物件的共同语言，可以保留。
- `relic_piggy_bank.png` 是最明确的离群项：粉色、正面头像感强、深色外轮廓弱，与相邻的旧金属、卷轴、晶体形成明显跳变；色数也远高于其余 89 张。
- 合同/账本/卷轴、护腕/胫甲、镜片等类别有相近剪影。大图能认清，不代表在 32 像素槽位中能迅速区分，应选这些家族做灰度和缩略检查。
- 可见包围框最长边约 25～31 像素；此外，空心项链与实心箱子的视觉重量也不同，不能只按包围框机械放大。

### 武器

- 长矛、弓箭、链锤依靠细杆、弦和链节表达结构；书和钱袋是集中块面。放进相同方格后，前者天然显得轻、小，后者显得饱满。
- 当前细长物件大多占满对角线，但线条仍细。这不是简单“裁掉透明边”就能解决的问题，适合针对 32/36 等实际需求单独整理轮廓。
- 建议先做小图标版本，并以缩略尺寸验收；64 像素稿可以继续用于较大展示。

### 附魔

- 16×16 本身不是缺点，作为状态符号可以很有效；问题在于它与物品图标的定位不够清楚。
- 分裂、水、风等仍依赖色相和少数笔画区分，放在低对比界面时需检查剪影。
- 先选择清晰的 16 或 32 显示档；如果希望与遗物并列为完整物品图，再按同一风格重新设计 32 像素稿。

证据：`scripts/ui/item_inventory_card.gd`、`scripts/ui/weapon_strip.gd`、`scripts/ui/preparation_offer_card.gd`、`scripts/ui/enchantment_inventory_card.gd`、`scripts/ui/enchantment_slot_card.gd`、`scripts/ui/enchantment_workbench.gd`。

## 7. 主界面：目前与局内的风格距离最大

- 背景为 1920×1080，具有平滑云雾、透视光照和大量渐变，约 88,786 种可见 RGB；视觉上是插画而非与局内相同的像素场景。
- 标题是 700×160 的立体金色艺术字，约 1,095 色，约 4.95% 可见像素使用部分透明；按钮是 600×186、约 2,151 色，也有抗锯齿边缘。两者本身就不是硬边低色数像素稿。
- 按钮节点只有 150×42，采用保持比例居中；源图有效主体约 438×173，还含较多左右透明边。换算后可见按钮主体约 **99×39**，文字却是 15px。实际截图中按钮因此显得小而挤，并不是文件 600 像素就会显得“高清又大”。
- 标题节点还使用 0.8 倍缩放。首页纹理没有显式设置最近邻，运行时根视口确认为线性过滤；战斗世界则是最近邻。**两处的采样规则确实不同。**
- 首页之后的角色选择页又切换到金线、暗色块面、像素字体，缺少连续的视觉语言。

建议先决定首页是否允许插画式封面。如果保留插画，标题、按钮及选角页仍需共用 UI 规范；如果追求全项目像素统一，应制作专用像素背景与标题，而不是把当前插画简单改成最近邻。按钮先校正透明留白、可见尺寸和文字比例。

证据：`assets/ui/main_menu/`、`scenes/ui/main_menu/main_menu_ui_controller.tscn`、`scripts/ui/main_menu_ui_controller.gd`、本次运行时过滤记录。

## 8. “模糊”应分成四类处理

| 类别 | 本项目例子 | 处理原则 |
|---|---|---|
| 原图就有平滑渐变、密集细节 | 首页背景/标题、属性栏金属与皮革 | 需要风格化整理或重新设计；Nearest 不能补救原图表达 |
| 引擎插值软化 | 首页继承根视口线性过滤 | 明确该图属于像素还是插画，再选择采样；不要全局盲改 |
| 非整数缩放导致线宽不均/细节丢失 | 属性框 292/313、石台 0.64、武器 34/64、附魔 20/16 | 优先使用目标尺寸版本与稳定倍率；Nearest 可减少软化但不能避免丢线 |
| 明暗、特效及信息过密造成“看不清” | 深色怪与湿地、小字压木纹、弹窗后景模糊 | 改善对比和层级；按用途保留背景效果 |

全部 214 份正式 PNG 导入配置为 `compress/mode=0`、`mipmaps/generate=false`，没有证据支持“全项目都因有损压缩或 mipmap 而糊”。

**还存在窗口级的第二次缩放。** 本次 1920×1080 运行记录为：窗口 1920×1080、逻辑可见区域 1152×648、`content_scale_size=1152×648`、世界 SubViewport 1152×648。因此该截图是逻辑画面整体放大约 1.667 倍，不是世界按 1920×1080 原生渲染。即使精灵内部是 1 倍最近邻，最终屏幕也未必一对一呈现源像素。这与旧清晰度文档中“世界视口与窗口始终一致”的表述不能直接互相替代，应以当前运行记录为准。整改必须覆盖整条链路，而不只修改 Sprite2D 的 filter。

`shaders/ui/modal_backdrop.gdshader` 明确使用半径 3 的九点背景模糊；这是弹窗后景效果，不应作为素材损坏的证据。CRT Shader 主要增加扫描线与暗角，不等于对整个战斗做模糊。

全局字体使用 12px 方舟像素字体，但各处常用 10、11、14、15、22、25 等字号；字体导入关闭抗锯齿。字体小且笔画密，会进一步强化“糊/挤”的感受。字号应独立验收，不能只换 PNG。

## 9. 建议整改顺序与验收标准

1. **先确定一套实际可用的样板。** 选玩家、普通怪、骑士、石台、一个 UI 框、遗物/武器/附魔各几张，摆进同一真实界面。确定角色比例、描边、光源、色板倾向与 UI 材质。可优先沿用现有低饱和青灰/旧金/苔绿方向，但这属于建议，不作为已批准的最终画风。
2. **先修无需重画的呈现问题。** 先明确逻辑视口到窗口的缩放策略，再整理图标显示档位、按钮留白、属性栏基准宽度、木纹平铺、过滤继承和字体规格。保留现有素材进行前后对照，确认收益。
3. **统一属性栏和理财组件。** 两者会同时出现在屏幕上，应第一批一起验收，随后推广至商店、选角、设置和首页按钮。
4. **整理战斗主体与环境。** 优先角色可读性、骑士/玩家比例语言、石台颗粒与外围对比；天空与地表的细节节奏随后调整。近景和远景可以有差别，但必须服务空间层次。
5. **局部修图标，最后成批推广。** 优先猪猪存钱罐、细长武器缩略图和附魔显示倍率，再处理相似剪影。保留已经合格的图标。
6. **更新规范，结束新旧规格并存。** 当前规则文档一边要求武器 128×128，实际全部为 64×64；玩家又同时出现四帧规则与八帧实况；首页 README 的按钮尺寸也与实际不符。这些冲突应在方向确定后统一更新。
