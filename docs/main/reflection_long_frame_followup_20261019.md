# 反射长帧与测试失败复核（2026-10-19）

本次补充了帧阶段测量，修正了 5 项过时或存在时序竞争的测试，并把反射绘制预热加入地下城加载界面。**不能宣称原先的 415 ms 峰值已经彻底修复。**

## 长帧发生在哪里

### 原先的 415.167 ms

固定压力测试第二轮第 34 步：1,280 束反射参与更新，第一批 320 束达到生命周期末尾，反射更新计时 56.171 ms（其中伤害回调 11.604 ms），背景更新 1.409 ms。原记录没有覆盖剩余阶段，所以“此时正好释放反射”只是时间上的重合，不能据此把约 359 ms 的差额全部算作释放成本。

新增诊断场景在 `process_frame`、`frame_pre_draw`、`frame_post_draw` 之间记录墙钟时间，同时记录反射 `tree_exiting` 的数量和起止时间。另存渲染器计时值作参考，不使用更新较慢的 `Performance.TIME_PROCESS` 去解释单个尖峰。

首组 4 轮重跑，每轮仍为 96 只怪物、1,280 束反射、60 个固定模拟步骤。最高帧分别为 **110.329 / 93.104 / 178.003 / 118.975 ms**，没有重现 415 ms。

- 16 次批量退出中，每次 320 束，首末退出信号的跨度为 **3.483–6.868 ms**。
- 该跨度包含多数节点的退出/释放过程，但不等于完整的析构、渲染资源回收成本；不能据此承诺对象池只值几毫秒，也不能把原尖峰全部归因于对象销毁。
- 稳定负载仍较重：各轮反射更新平均 **34.889–53.023 ms/帧**，其中真实伤害回调平均 **9.192–15.758 ms/帧**；整个绘制阶段平均 **8.249–10.704 ms/帧**。
- 伤害耗时包含在反射更新耗时中，两者不能相加；静止怪物的自主逻辑没有参与正式测量区间。

### 新捕捉到的 485.766 ms

后续诊断中又出现一次数百毫秒尖峰，这次阶段记录完整：

| 同一帧的阶段 | 耗时 |
|---|---:|
| 更新开始到绘制开始 | 106.575 ms |
| 其中：生成 320 束反射 | 29.768 ms |
| 其中：反射更新，包含伤害 | 56.948 ms |
| 绘制开始到绘制完成 | **379.269 ms** |
| 当帧退出的反射 | **0 个** |

尖峰出现在第 0 步，而非到期批量释放的第 34 步。因此，当前至少存在一种**首次可见绘制阶段的尖峰**。这个阶段同时包含绘制回调、渲染提交、驱动/同步等待，不能直接称为“GPU 算了 379 ms”或“已经证实着色器编译耗时”。本机 Compatibility 后端的 GPU 计时为 0，也不足以继续拆分。

这解释了一个可复现的长帧类型，但原 415 ms 缺少阶段记录，仍不能确认两次尖峰完全同源。

## 能否继续优化

| 方向 | 本次处理与判断 |
|---|---|
| 首次反射绘制 | **已补充加载预热**：黑幕期间实际绘制完整、简化、最低可见三个等级的反射样本，提前触及其材质/绘制路径；样本不处理伤害、不播放音效、不占视觉预算，加载结束一并移除 |
| 持续反射更新 | 仍是主要 CPU 负载；下一步优先减少每束反射对已命中目标的反复检查，并复用不变的属性解析结果，保留实时伤害和状态结算 |
| 节点创建与释放 | 可继续研究复用，但当前数据不足以把它排在数百毫秒尖峰的唯一根因位置；需要同时量到渲染资源释放阶段 |
| 驱动/绘制提交的偶发尖峰 | 保留分阶段追踪；如预热后再现，需要进一步抓取引擎/驱动时间线，而不是靠删除高耗时样本宣称修复 |

预热验证组 4 轮的首个战斗绘制阶段为 **16.996 / 9.975 / 8.470 / 14.936 ms**，全程最高帧为 **159.556 / 141.779 / 123.863 / 134.241 ms**，没有出现 400 ms 级峰值。该组平均帧耗时仍为 **59.879–70.002 ms**，所以预热不能解决持续 CPU 负载，也没有依据宣称稳定 60 FPS。不同轮次存在明显波动，本次不计算“预热提升百分比”。

预热验证使用加载结束后的额外绘制样本，确认方法可运行；正式改动把三个代表性样本放在已有黑色加载遮罩下面。两者均执行真实绘制，隐藏节点或只 `preload()` 资源不能替代这个步骤。

**正式接入后的再次验证：**关闭诊断场景的额外预热，仅走正式加载流程，4 轮最高帧为 **106.425 / 85.748 / 83.915 / 142.747 ms**，首个战斗绘制阶段为 **19.443 / 8.123 / 7.861 / 12.792 ms**；240 帧平均 **54.381 ms**。本组没有出现 400 ms 级峰值，所有伤害/视觉签名仍一致；这属于有限次数的复测结果，不是偶发峰值永不再现的保证。

另试验了循环内局部数组引用、提前跳过已命中对象的微调，完整帧耗时没有稳定收益，已撤回，正式反射结算实现保持上一轮版本。

## 5 项测试为什么失败

优化前的隔离代码已复现相同失败；本次进一步取得了实际碰撞与参数数据。

怪物碰撞体是横向胶囊，局部包围框为 `(-30.6, -12.0), size=(60.0, 26.4)`，并非以角色位置为中心、半径 13.2 的圆。

| 失败项 | 实际原因 | 修正后的验证 |
|---|---|---|
| 冰面椭圆边缘的“范围外”目标 | 旧测试把胶囊端帽半径 13.2 当作水平半宽；实际水平半宽为 30，所谓范围外的身体仍与冰面重叠 | 从碰撞体变换后的包围框取得横纵尺寸，分别测两轴的接触内外边缘，并继续检查扩大后不重复扣血 |
| 初始冰面不应命中 x=70 的目标 | 目标左缘约 x=39.4，已进入半径 51.2 的冰面；实测 HP 为 9,975，正确受到 25 点伤害 | 将整个身体放到初始冰面之外、风扩大后的范围之内 |
| 致死电火花应对附近目标造成 180 点爆炸伤害 | x=50 的身体左缘约 x=19.4，已接触半径 20 的落雷，实际既受 60 点落雷伤害，又受 180 点爆炸伤害，最终 HP=9,760；爆炸另经调度器结算，原等待也可能过早读到 HP=9,940 | 同时检查 x=50 的双重命中和 x=80 的仅爆炸命中（HP=9,820），并在最多 6 个处理帧内等待后者的接触结果 |
| 火焰初始不应点燃 x=55 的目标 | 身体左缘约 x=24.4，已经进入半径 30 的火焰，实际燃烧状态为 true | 将身体完整移出初始圆，再检查风扩大后首次进入 |
| 领域加成后的风刃半径必须是 16.1 | 16.1 来自旧值 14×1.15；当前弓箭基础接触半径为 17，实际结果为 **19.55=17×1.15**，速度 480、时长 0.46 未变 | 验证相对当前基础宽度的 1.15 倍关系、飞行参数不变，以及扩大边界内命中/边界外拒绝 |

修正的是测试夹具位置、过时数值和等待条件；没有把碰撞体缩回旧尺寸，也没有删减电火花或爆炸伤害。
