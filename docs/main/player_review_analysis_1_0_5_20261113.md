# 玩家长评分析（1.0.5 · TapTap「哥布林教你地下城的评价」）

本文只做一件事：把这条评论拆成可核对的条目，逐条对照当前代码与项目自有文档，判断"成立 / 部分成立 / 误判但体验成立"，并给出根因与优先级。

结论先行：

- 评论 6 条里，**5 条成立、1 条技术误判但体验成立**。整条评论没有情绪化编造，它描述的东西基本都能在仓库里找到对应的实现。
- 六条抱怨背后只有一个共性：**本作所有跨系统耦合的输出都是"一个更大的数"，没有一条耦合输出"一条新规则"**。所以机制内部有联系、机制之间没有联系——玩家能感到"有联动"，但决策层永远是同一根数轴上的比较。
- 最该先修的两件事不是数值，而是**受击可逃逸性**（被打之后玩家有没有办法活下来）与**移动端面板/字号**（玩家有没有办法读到信息）。这两条不修，其余改动都会被"被秒"和"看不清"盖掉。

## 2. UI：不是美丑问题，是没有排版体系

**多字号是真的，而且不是"一句话里故意做层级"。**

`scripts/ui` 下的字号覆盖统计：

```
9 10 12 13 14 15 16 17 18 20 22 23 24 26 27 30 42   ← 17 种
```

同一屏内实例：

- 战斗 HUD：`combat_hints` 12、`exp_label` 12、`wave_label` 20、`drawer_toggle_button` 24/26 → 2 倍差；
- 结算回执：标题 24、摘要 13、金额 26、明细行 12（`scripts/ui/interest_settlement_popup.gd`）；
- 结算面板：返回按钮 18、击杀记录另算（`scripts/ui/run_settlement_panel.gd`）。

12px 与 13px 在像素字体上几乎不可区分，却分属两个不同组件——这说明字号是"每个控件自己定的"，没有全局尺度。玩家看到的"一句话好几个字号"，实际是"同一层级的信息被三套字号各自表述"。

**遮挡是已知问题，不是玩家错觉。** 项目自己的移动端文档把这类问题列为待办第一条：

> 浮层/面板在 1324×745 逻辑视口下的排版：45 条移动端新增失败集中在同一族问题——按 `viewport/1920` 等比缩面板，但字号是绝对值。

并在另一处明确记录：

> 本次功能修改未处理之前视觉检查中记录的其余天赋面板遮挡、利息回执、奖励字号与结算触屏滚动问题。

机制上：桌面按 1920×1080 绝对坐标摆版，移动端只把整卷放大 1.45 倍（`autoloads/mobile_profile.gd`），字号按绝对值放大而面板按比例缩，两者不同步 → 文字溢出压按钮。这是**设计层面的做法问题**，不是某几个坐标没调。

**建议（按收益）**

1. 建立 5 档字号 token（如 12/16/20/24/32），禁止组件内写字面量；现有 17 档先映射再删。
2. 面板一律"最小宽度 + 换行 + 触屏滚动"，禁止"按比例缩"；可以照 `mobile_bank_test` 的断言模板（只断言控件在视口内、Label 不溢出）推广到所有面板。
3. 加一条自动检查：战斗 HUD 内任意两个可点击控件的矩形不相交、任意 Label 的 `get_minimum_size()` 不超出父面板。这项检查能一次性拦住"图层压按钮"。

## 3. 双轨机制：后期没有"提款"的理由，所以双轨必然塌成单轨

机制本身是清楚的：

- 本金每波结息（默认 5%，`scripts/rewards/battle_finance_system.gd`）；
- 本金可买武器升级：100 / 200 / 350 / 500，**每波 1 次**、全武器共享配额（`scripts/rewards/weapon_upgrade_rules.gd`、`scripts/core/main_flow_coordinator.gd`）；
- 本金同时支撑 **7 件** `derived_stat_from_principal` 遗物（保险柜/量化操盘/恶意收购/并购重组/金币心脏/囤积者戒指/黄金测距仪）与"本金复活"。

问题出在量级和寿命：

| 项 | 数值 | 结果 |
|---|---|---|
| 本金 500 的每波利息 | 25 金 | 战斗收入是它的 5～20 倍 |
| 单次武器升级（商店金币价） | 20～60 金（按稀有度），不随等级涨价 | 一个拾取物的金币量级就能买 |
| 武器升到 Lv5 的本金总价 | 1150，每波限 1 次 | **第 5 波左右封顶** |
| 第 1 波战斗收入（按配置推算 ≈35 只 × 4） | ≈140 金 | 首波就能买 3～5 次升级 |
| 武器封顶后本金的负作用 | 无 | 只剩利息、属性、复活保护三重正收益 |
| 本金封顶后新增的需求 | 无 | 没有通胀、没有挤兑、没有侵蚀联动 |

（金币与经验同源：经验球的 `collected` 信号把 `amount` 同时当作金币发货，`scripts/pickups/exp_orb.gd`。）

于是：**武器封顶 = 双轨制的玩法寿命结束**。第 5 波之后，"存款还是提款"不再是一个决策——存钱严格优于花钱（利息、属性、复活全都朝一个方向）。玩家感受到的"前期非常短，一旦稍微成型就立刻进入滚雪球"，本质是"唯一需要权衡的资源在第 5 波之后不再需要权衡"。

这也解释了评论里"这个机制和游戏内容不怎么相关"：它相关，但只在**前 5 波**相关；之后银行面板仍然每波弹一次，却不再改变任何选择，只剩下仪式感。

**建议**

1. 给中后期本金一个新的"支出理由"或"持有风险"，让提款重新变成决策：
   - 本金越高侵蚀越高（或夜间追击强度随本金上升），把"贪婪"从文案变成机制——这本就是 `project.md` 里写的主题；
   - 或让武器满级后的成长只能从本金走（本金 → 附魔槽/专精/负载），把金币出口关掉，强制转轨。
2. 把利息从"固定 5%"改成"与本金规模递减"，避免大本金自我强化。
3. 若保留固定利息，至少要有一个"提款才能买到的东西"，否则单轨最优解会被玩家快速算出。

## 4. 数值与元素：黑洞对冻结是严格支配

| | 黑洞 | 冻结（冰场） |
|---|---|---|
| 作用半径 | ≈95（`_sphere_radius × 3`） | 51.2 |
| 伤害系数 | 0.45 × 元素伤害 | 0.25 × 元素伤害 |
| 控制 | 拉向中心 0.85 秒 + 黑暗 2 秒 | 减速到 0.6（3 秒）+ 冻结 1 秒 |
| 附加收益 | 把怪聚成一团，**放大后续所有 AoE 与链跳** | 无 |
| 命中方式 | 每只怪结算一次 | 每只怪结算一次（同样只结算一次） |

黑洞不只是"更强的控制"，它还**改变了后续伤害的空间效率**——聚怪让每一发范围伤害多打几倍目标。冻结在同样的槽位里只提供"怪不动"，且半径与伤害系数都更低。所以"选黑洞，然后无脑选伤害最高的配合"不是玩家偷懒，是这一组选项本身存在支配关系。

元素反应系统是存在的（电+燃烧引爆、黑暗+火等），但反应产物仍然是"一次更高的伤害"，所以玩家的总结"除了冻结以外也只是更高的伤害和更大的范围"是对的。

**建议**

1. 给冻结一条**独立收益**：冻结目标受下一次直伤提高 / 冻结可被击碎并产生冰片 / 减速值转成控制强度系数——让它不再是"更弱的黑洞"，而是另一条线。
2. 给黑洞一条**成本**：聚怪把怪拉到玩家身边，这在本作恰好最致命（见下一节）。保留聚怪作为风险收益，而不是纯收益。
3. 元素反应的输出从"伤害"改一两条成"规则"：例如湿润使闪电路径可导电（范围判定而非伤害），燃烧给护盾加破甲标记。哪怕只有两条，玩家的表述就会从"纯物理配合"变成"这套组合有讲究"。

## 5. 受伤机制：0.1 秒无敌帧 + 只推怪不推人 + 反馈被自身频率吃掉

这一节是评论里最值得立刻动手的。先把事实钉住：

1. **有无敌帧，但只有 0.1 秒**：`DEFAULT_INVINCIBILITY_SECONDS = 0.1`（`scripts/player/player_controller.gd`），且 `take_damage()` 只在 `_invincibility_timer <= 0` 时生效 → **每秒最多 10 次接触伤害**。
2. **接触伤害每次物理帧都在判定**（`scripts/enemies/enemy_controller.gd` 的 `_process_contact_damage()`），唯一闸门就是上面那 0.1 秒。
3. **击退只作用于怪**：`_apply_contact_knockback()` 把**敌人**从玩家身边推开；玩家本身没有位移、没有弹开、没有短暂无碰撞。所以玩家一旦站进怪堆，会以 10Hz 的频率被动挨打，而自己没有"被弹出去"这个生理信号。
4. **反馈被频率吃掉**：受击只做一次 0.16 秒的红色 modulate 补间（`_apply_damage_flash()`），而伤害间隔是 0.1 秒 → 补间永远播不完，玩家在怪堆里是**持续泛红**，分不清"挨了几下"。这正是"毫无感知地掉血"的来源：反馈不是没有，是连续到无法计数。

算一下"被秒"：

```
小怪基础接触伤害 9 × 难度 0.45 × 波次成长（12 波 1.165）≈ 4.7
侵蚀 200 时伤害乘区 ≈ ×3.8 → 每次 ≈ 18
10 次/秒 → ≈ 180 DPS
100 血 + 300 盾 = 400 有效血量 → ≈ 2.2 秒
```

即便侵蚀为 0，也是 ≈47 DPS、约 8.5 秒——足够在"没注意到"的情况下见底。评论者说"一百多血三百多盾，难度一也会被秒"完全对得上；而且**难度 1/2/3 只差 20%～30% 的属性系数**（`scripts/data/battle_difficulty.gd`），主要差的是怪的数量上限（48/72/96），所以"难度一"不会因为难度而免于这套致死机制。

顺带一个呼应：黑洞把怪聚到玩家面前（第 4 节），而这里玩家没有任何脱离手段——**目前黑洞的最优用法和受伤机制是互相打架的**。评论者"一个黑洞把怪聚在面前，如果没秒掉，碰一下就死"不是操作失误，是两个系统没有对齐。

**建议（P0）**

1. 无敌帧 0.1 → **0.4～0.6 秒**，并把"护盾被击穿"与"生命受伤"分开计时（现在护盾吸收也消耗同一个无敌帧）。
2. 受击给玩家一次**可逃逸位移**（短击退或 0.2～0.3 秒无碰撞），让"被围住"变成可操作的处境，而不是纯等待。
3. 反馈改成**可数的单次**：受击跳一个伤害数字 + 短促震屏 + 血条掉块动画，去掉长期共鸣的红色 tint（或只在生命受伤时闪）。
4. 若保留"黑洞聚怪"，需要同步给玩家一个"聚怪后仍能活"的出口（例如聚怪范围内减伤，或黑洞吸引时推开玩家）。

## 6. 性能：发热与"丢包式卡顿"都有实测支撑

项目自有的性能记录（`performance_report.md`）：

| 场景 | 结果 |
|---|---|
| 侵蚀 200 / 怪物 +200% / 电浆炮满附魔 | GPU 平均 17.56ms，**P95 36.79ms，最大 67.91ms**，900 帧中 354 帧超 16.67ms |
| 4 武器满附魔 / 30 只移动怪 | 平均 21.55ms，**P95 54.51ms**，最大 121.64ms |
| 150 只怪 / 4 武器混合 | 过载到 **1762ms/帧** |

根因文档写得很清楚：不是"切武器"，是**每次命中的同步附魔/元素链扇出**（电浆每目标最多 5 次附魔 × 分裂 × 链跳 × 范围目标），以及 O(怪物数) 的选敌/排序/范围查询。

"丢包式卡顿"的两个来源：

1. **长帧期间画面不刷新**：一次 50～300ms 的尖峰里，屏幕就是"不刷怪"，恢复的那一帧把所有到期事件补齐——刷怪计时按 `delta` 结算（`_process_spawn_timers`），多个波组会在同一帧同时到期，于是表现为"静默一秒，然后被一群怪包围"。
2. **命中扇出尖峰**：`plasma_combo_live.json` 记录到 20～30ms 尖峰帧内同帧生成 15～34 个闪电效果——玩家看到的正是"卡一下、然后一堆东西同时出现"。

**发热**：Android 走 GL Compatibility + ANGLE，项目**没有设置帧率上限**（`Engine.max_fps` 只在测试脚本里出现过），战斗按 1080p 画布 + 1.45 倍 UI 放大渲染，特效无全局预算。手机持续满载跑 = 烫手。

**建议**

1. 移动端锁帧（默认 60，低端机 30），并提供"特效/粒子档位"开关；
2. 按 `performance_report.md` 的优先级做**每帧全局预算**（限制链跳、爆炸、范围查询、附魔生成数量），优先级高于继续压装饰；
3. 选敌/链跳/范围伤害统一走 `EnemyRegistry` 空间索引；
4. 加一个长帧检测器（>50ms 记录场景快照），把"偶发丢包"变成可定位的数据。

## 7. 统一解释：为什么所有机制"各自独立"

遗物共 101 件、`runtime_effects` 共 18 种效果类型。把**经济与战斗之间**的桥接全部列出来：

| 桥接 | 件数 | 输出形式 |
|---|---|---|
| 本金 → 战斗属性（`derived_stat_from_principal`，每 50 本金 +1 护甲/攻速…） | 7 | 标量 |
| 本金 → 额外复活/续命（`principal_revive`、破产重组的安全网部分） | 2 | 次数 |
| 金币 → 本金、侵蚀 → 利率、利息 → 利率成长 | 3 | 标量 |
| 加速结息（`extra_settlement_per_wave`、`settle_interest_every_n_waves`） | 2 | 更多同一个资源 |
| **真正改变规则的**（`block_stat_increase` 让理智永久不能回复、`bankruptcy_recovery` 破产重组） | **2** | 规则 |

也就是说：**经济和战斗之间的桥接（7+2 件）全部是"把本金换算成更大的数值或更多次复活"，真正输出规则的只有 2 件。** 元素系统同理——反应存在，但产物是伤害；武器升级的产物是附魔槽位数量。其它派生属性（`derived_stat_from_player_stat` 4 件）是"移速给护甲""侵蚀给护甲"这类同轴换算，仍然不产生新规则。

**所有耦合的输出都是"一个更大的数"，没有一条输出"一条新规则、一段新时序、一种新空间关系"。**（唯一接近时序的是 2 件加速结息，但它产出仍然是金币本身。）

这就是评论第 6 条真正的含义。玩家在**机制层**确实能感到联动（存钱会让护甲变高，很直观），但在**决策层**所有选择都会归约成同一根数轴上的比较——哪边数大选哪边。一旦玩家算出了这张表（大约第 5 波），剩下的游戏就是执行，于是"前期短、成型即滚雪球、细节欠缺打磨"是同一个现象的三个侧面。

对照 `project.md` 里写的主题（"资本裹挟思想，贪婪堕入深渊""为了解决上一个问题，不得不接受下一个问题"）——主题要求的是**规则级的互锁**，现在实现的是**数值级的并存**。这不是打磨不足，是设计与实现之间还差一层。

**建议的方向**：下一批内容不要加"+N"，加"如果…则…"的规则。例如：

- 本金超过某阈值时，夜间追击上限提高（贪婪 → 危险）；
- 护盾归零时黑洞自动触发一次（风险 → 收益，已经有 `TRIGGER_SHIELD_BREAK` 钩子可用）；
- 冻结目标死亡时对周围施加减速（控制 → 传染）；
- 提款超过本金 30% 时本波掉理智（花钱 → 代价）。

## 8. 优先级

**P0 —— 玩家会因为这两件事流失**

1. 受击可逃逸性 + 可感知的受击反馈（0.1s → 0.4~0.6s、一次击退/无碰撞、单次可读反馈）。
2. 移动端面板遮挡与字号体系（已有 45 条失败清单与 `mobile_bank_test` 断言模板可推广）。

**P1 —— 决定"耐不耐玩"**

3. 本金在中后期的需求或风险（让提款重新成为决策）。
4. 武器满级后的金币出口（否则商店在第 5 波后变成装饰）。
5. 冻结的独立收益 / 黑洞的成本（消除支配关系）。

## 9. 需要为评论者澄清的三点（也说明我们的问题）

1. **无敌帧存在**，0.1 秒。评论者说"没有"，是因为 0.1 秒在 60fps 下是 6 帧，且玩家没有任何"我进入了无敌"的视觉/位移信号。
2. **打击停顿（hitstop）已经关闭**：`HITSTOP_SECONDS = [0,0,0,0]`，只剩震屏。"丢包卡顿"不是打击停顿造成的。
3. **移动端做过一轮适配**（`MobileProfile` 单例、150+ 行平台分支、多轮实机反馈修复记录，见 `docs/mobile/mobile_adaptation_status.md`），但适配结论是"技术路径对、排版没跟上"，所以玩家的体感依然是"没有针对手机优化"。

三点放在一起是同一个教训：**在玩家感知不到的维度上做对，等于没做**。这比"没做"更需要优先解决，因为它会持续产生"玩家说的和我们知道的不一样"的错位。

## 10. 可以回给玩家的三句话（可选）
