# 主战斗场景性能实测（2026-10-19）

本文记录当前工作区的实测结果，包含尚未提交的主战斗、武器接触规则和 HUD 修改；不能当作某个已发布版本的成绩。测试代码只做测量和对照，不修改正式游戏的攻击伤害、怪物数量上限或打击停顿。

**当前优先级：大量元素反应的实例与集中结算、坤舆法阵绘制、运行时地形补块。** 草簇的常规绘制和 96 只普通怪物逻辑会增加持续负载，但不足以解释本轮最严重的数百毫秒至一秒长帧。高平均 FPS 也可能掩盖反应爆发和主动打击停顿。

## 测量条件

- Godot 4.7.2，Compatibility / ANGLE / Direct3D 11；Intel Core Ultra 5 125H、Intel Arc 核显，驱动 31.0.101.5333。
- 真实 GameRoot、主战斗地形与 HUD，世界 SubViewport 为 **1920×1080**；关闭垂直同步和帧率上限。
- GPU 测试全部运行于独立 Windows 桌面；运行器验证实际引擎桌面并记录 `foreground_samples=0`，不切换用户桌面。
- 使用临时游戏会话。控制测试关闭自然刷怪，普通战斗按约 70% 蛆虫、30% 蝙蝠配置。敌人保留原有行为、碰撞、受击和状态逻辑，生命值提高以稳定数量，玩家无敌。
- 正式难度的普通怪物上限为 48 / 72 / 96。96 是主要场景；192 **超过正式上限**，仅用于看增长趋势。
- 子系统对照每项 3 秒预热、5 秒统计，两轮，第二轮反向执行。固定玩家位置，避免怪物挤动玩家造成不同地形；另测真实移动。
- 单武器保留正式冷却、攻击次数与命中流程，每项 12 秒，前 2 秒单列为首次使用窗口，后 10 秒统计。各项均核对成功施法和实际伤害。它们在同一进程中依次测试，因此首次窗口不等于清空全部驱动缓存后的冷启动。
- 上述时长是采样目标；无法在一个阻塞中的游戏帧内中止计时，长帧可能使实际时长超出目标，明细另列实际秒数。
- 附魔隔离测试保留真实元素反应，以每秒 2 个元素序列触发，96 个目标限制自主移动；不是声称正式武器每秒都触发 2 次，也不包含所有流派的命中频率。
- 取 `frame_post_draw` 的墙钟间隔；测量期间不截图、不读取 GPU 纹理。记录平均、P95、P99、最大帧耗时，以及超过 33 / 50 / 100 毫秒的次数。
- CPU 计时包装原有怪物、伤害、地形、调度器和部分绘制回调，均是**包含内部调用的耗时**，不能相加推导各模块百分比。`Performance.TIME_PROCESS` 等监视值刷新较慢，首次窗口可能残留加载阶段数据，因此不用于解释单帧峰值。
- 打击停顿会暂停世界约 50 毫秒，但主窗口仍可绘制；帧率数字不能反映这段冻结，另外记录停顿触发事件。

## 已确认的路径

### 多段命中叠加元素反应

正常冷却、合法附魔槽位、96 个高生命值目标下：

| 组合 | 等级 | 后 10 秒平均 / P95 | 最大帧耗时 | 12 秒伤害事件数 |
|---|---:|---:|---:|---:|
| 电浆炮＋火焰＋闪电链 | 2 | 17.5 / 47.6 ms | 203.2 ms | 27,267 |
| 电浆炮＋火焰＋电火花 | 2 | 25.2 / 70.2 ms | 435.9 ms | 24,773 |
| 电浆炮＋水＋冰＋光 | 4 | 22.0 / 88.5 ms | 1,171.6 ms | 31,392 |
| 赤铜炉灯＋分裂＋火焰＋闪电链 | 4 | 21.5 / 61.7 ms | 209.1 ms | 3,075 |

火焰＋电火花的一帧中，`EffectScheduler._process()` 连同内部回调耗时 **244.28 毫秒**，该帧结算 2,159 次伤害，总帧耗时 435.89 毫秒。另一帧结算 **4,498 次**伤害；整轮最大达到 **4,771 次/帧**。耗时主要落在执行反应、范围查找和伤害等回调链，不能把这个数字解释成调度器数组操作自身用了 244 毫秒。

水＋冰＋光组合同时存在过 **1,279 个 reflection 实例**，另有 164 个冰领域、147 个水效果、147 个光剑效果。`LightReflectionEffect._process()` 每个实例都推进时间并执行 `_damage_sweep()`；即使视觉预算把装饰隐藏，逻辑实例仍扫描候选并结算。原有空间索引和单束已命中缓存能够降低单次搜索成本，但无法阻止实例数量倍增。

独立复测再次出现 **566.81 毫秒**长帧和 1,200 个反射实例；反射实例的更新回调合计单帧 **229.94 毫秒**，该帧共结算 5,432 次伤害，直接证实逻辑更新本身也是热点。隐藏反射画面的诊断轮仍出现大量逻辑实例，但施法推进、反应次数和实际采样时长发生明显分化，**不作为等负载性能收益对比，也不据此判断隐藏画面会更慢**。该诊断轮的极端最大帧尚未完整归因。

这里的高生命值目标会持续承受反应，普通低血怪被击杀后负载可能更早结束。因此这是合法武器配置在高存活密度下的压力结果，不是断言所有普通战斗都会卡一秒；但相同帧内成千上万次结算已经是明确的扩展性问题。

优先优化方向是共享候选查询、复用同帧不变参数、减少重复构造与遍历，并检查同一施法对同一目标生成反射的频率。若要合并伤害或限制反应生成次数，需要单独确认其对伤害、暴击、状态消耗和连锁规则的影响，不能只为帧率悄悄改变战斗结果。

### 附魔隔离结果

固定每秒 2 个元素序列时，火焰＋电火花有约 **86–91 毫秒**峰值，一帧 1,352 次伤害；水＋冰＋光峰值约 **89 毫秒**。黑洞后段平均约 **17.3 毫秒**，火焰＋黑洞约 **18.8 毫秒**，属于更持续的负担。其它单元素在本轮大多低于这些组合，但这不代表在任意投射物数量、等级和触发频率下都没有问题。

`explosion` 卷轴当前走 `_shockwave()`，是纯击退控制，伤害事件数为 0 是预期；不能将其当作雷火爆炸的伤害性能。普通粒子世界的计数也不覆盖所有闪电批次和着色器效果，不能凭这个计数低就排除特效开销。

补测的火焰＋电火花对照里，完整效果与关闭跳字、闪白、雷火视觉的伤害事件数均约 1.95 万，负载相近。关闭这些显示项后，调度及反应回调单帧仍约 **16–23 毫秒**，没有消除集中结算。数字显示和闪白有额外成本，但本轮不是唯一根因。关闭打击停顿后的平均帧耗时反而上升，因为世界不再冻结，不能把这解释成打击停顿降低了真实战斗响应延迟。

### 移动中的地形补块

`CavernBattleBackdrop._update_area()` 仅在 `battle_loading` 为真时使用约 4 毫秒预算；正常战斗会在同一帧清空 `_pending_cells`。补块还会生成草簇、排序、构建前后两组 MultiMesh、创建碰撞体和灯光材质。

两轮真实移动对照的最大帧耗时为 **83.57 / 124.76 毫秒**；隐藏草簇绘制后仍有 **88.17 / 79.65 毫秒**。不输入移动时，怪物也可能挤动玩家并触发镜头补块。初步自由玩家对照中，一个地形更新回调耗时 **86.55 毫秒**；武器测试中也有长帧几乎全部耗在地形更新，且该帧没有命中事件。

因此，草簇的“生成/上传”和草簇的“日常绘制”必须分开处理。优先把正常战斗补块纳入预算，在远离可视边界的预留区域提前生成，再考虑资源复用。

### 坤舆秘仪书法阵绘制

`RitualDomain._draw_domain()` 每次重绘包含 144 个边缘方块、24 个外围方块和符文。方块经 `_draw_domain_square()` 动态构建多边形，并逐个调用 `draw_colored_polygon`。

首轮出现 **250–495 毫秒**的连续长帧。专门复测时，绘制回调单次最高 **138.77 毫秒**；停止怪物物理逻辑后仍达 **529.18 毫秒**，该帧总耗时 **597.61 毫秒**；隐藏草簇也没有消除。隐藏法阵绘制后，绘制回调开销归零，同轮最大帧下降到 **111.01 毫秒**，余下峰值仍包含地形补块。命中/武器更新回调峰值约 **15–16 毫秒**。

瓶颈已经缩小到法阵绘制和图形命令提交路径。当前计时不能继续区分 Godot 内部多边形处理、驱动同步和 GPU 时间。建议用保持像素对齐的矩形批次或预分配实例替代每帧重建小多边形，保持 168 个方块的位置、数量和法阵范围，再做画面与性能对照。

### 怪物逻辑与草簇的持续开销

固定玩家位置的两轮结果，96 怪物、玩家不攻击时，平均帧耗时 **11.41 / 11.62 毫秒**。停止怪物物理更新后为 **9.96 / 10.44 毫秒**；停止地形 CPU 更新后为 **10.77 / 9.86 毫秒**；仅隐藏草簇为 **11.04 / 10.44 毫秒**。这些是整帧结果，不是各模块的独占耗时。

96 只怪物的原逻辑回调合计平均约 **1.19 毫秒/渲染帧**，地形回调约 **1.9 毫秒/渲染帧**。192 只的怪物回调增至约 **3.47–5.97 毫秒/渲染帧**，整帧平均 **16.50–22.72 毫秒**。怪物种类、拥挤程度、攻击状态、每帧物理步数都会影响结果，不能按数量简单线性外推；本次 48 只场景也未稳定快于 96 只。

测试驻留约 2.4 万株草、470–500 个前后景批次节点，**这是驻留量，不是屏幕实际可见量**。草簇已经批量绘制，固定镜头下不是这轮数百毫秒卡顿的首要原因；移动中仍有值得优化的生成开销。

### 设计中的打击停顿

`CombatHitFeedback` 在同一攻击的局部新命中数量跨过门槛时，会设置 `SceneTree.paused`，并冻结世界视口，每次约 **50 毫秒**。

单武器 12 秒测试中：电浆炮 15 次、赤铜炉灯 17 次、营地短刀 21 次、流星摆锤 27 次。这会造成可感知的频繁冻结，即使平均帧率仍然很高。它是现有打击感规则，与程序计算卡住是不同来源。可考虑增加全局触发间隔，或限制持续攻击中同一施法的停顿次数；这属于手感调整，应单独验收。

## 结果边界

本测试主要隔离稳定怪物数量下的负载，不代表首领、精英怪技能、死亡掉落、升级弹窗、全部武器等级和全部附魔排列已经覆盖。单个偶发最大帧也不等于已确认根因；有重复复现、回调计时和关闭对照的路径，证据更强。不同轮次存在地形细节和运行负载波动，不把小幅差异解释成精确收益比例。

验证期间工作区新增了 HUD 图片，一轮对照因尚未导入而产生脚本错误；该轮保存为 `dense_cost_ablations_invalid_imports*`，不用于结论。重新运行无界面资源导入后补测。早期未固定玩家的对照只用于发现挤动导致的补块，不作为严格子系统对比。

## 建议的优化顺序

1. **处理反射实例增长和雷火集中结算。** 同时看实例数、每帧伤害次数和回调时间；只降低粒子数量不能处理这部分逻辑。
2. **替换法阵每帧的小多边形重建路径。** 保留外观、像素对齐和范围，改用可复用的矩形/实例数据；这是独立于怪物 AI 的重绘热点。
3. **把战斗中的地形补块分帧执行。** 用现有远处预留区域提前生成，避免单帧清空补块队列。随后再做网格、节点和材质资源复用。
4. **补充其它武器首次使用的预热。** 本轮赤铜炉灯第一次喷射约 298 毫秒，其它武器也有首次峰值。应先区分材质首次使用、批量受击资源创建和真正持续开销，避免只覆盖初始弓箭。
5. **单独调节打击停顿频率。** 持续攻击中每隔几个新目标暂停 50 毫秒，会加重“卡住”的感觉；不能通过平均 FPS 验收。
6. **最后再扩大普通怪物和草簇的常规优化。** 如缓存不变的地形材质参数、降低非关键视觉更新频率、为自动索敌先做粗筛；保持碰撞与攻击范围不变。

完整的 14 种武器、17 项附魔隔离、合法流派组合和子系统对照见 [测量明细](../../artifacts/reports/dense_combat_cost_tables.md)。本轮交付为诊断工具、原始数据与分析，以上正式性能改动尚未实施。

## 复现入口

场景：`res://scenes/tests/dense_combat_cost_review.tscn`。

运行示例（Windows PowerShell）：

```powershell
python scripts/tools/run_godot_background.py --godot 'D:\soft\Godot_v4.7.2-stable_win64.exe\Godot_v4.7.2-stable_win64.exe' --log artifacts/reports/dense_cost_recheck.log --timeout 360 -- --path . --scene res://scenes/tests/dense_combat_cost_review.tscn -- --transient-session --suite=weapons --report=artifacts/reports/dense_cost_recheck_metrics.json
```

可用套件：`subsystems`、`weapons`、`enchantments`、`builds`、`ablations`、`ritual`、`reflection`。`--only=` 接受逗号分隔用例；`--repeats=2` 第二轮反向执行。运行器的 `.json` 是独立桌面验证记录，测量报告使用 `_metrics.json`，避免覆盖。

`python scripts/tools/summarize_dense_combat_cost.py` 检查日志、退出码和独立桌面证明后生成测量明细；有脚本错误的运行即使返回退出码 0，也会被拒绝汇总。
