# 手机端稳定 30 FPS 方案（2026-11-17）

## 0. 目标与换算

用户真机现状：**5–10 FPS**，即 100–200 ms/帧。目标：**稳定 30 FPS**（33.3 ms，且 1% low 不低于 25）。

桌面同配置实测（七武器 5 级 + 分裂/火焰/闪电，48 个移动高血量敌人，自动施法，12 秒后台 GPU 采集，`foreground_samples=0`）：

| 指标 | 数值 |
|---|---|
| 帧率 | 29.95 FPS |
| wall | mean 33.39 ms / p95 141.5 / p99 202.1 / max 395.6 |
| `engine_process_ms` | 20.25 |
| `engine_physics_ms` | 45.50 |
| draw calls | mean 809 |

桌面到真机的经验倍率是 **3–6 倍**（CPU 与 GPU 都算）。因此：

> **要让手机稳定 33 ms，桌面同一场景必须做到 5.5–11 ms（90–180 FPS），或者手机端走降级路线（内部分辨率 + 特效预算 + 密度上限）。**
> 现在桌面是 33 ms，差距 3–6 倍。这不是"再优化几个函数"能补上的量级，必须动结构。

## 1. 关键判断：预算已爆表，并且在债务螺旋里

`engine_process_ms`(20.25) + `engine_physics_ms`(45.50) = 65.8 ms，**已经超过 wall 的 33.39 ms**。

这说明单帧预算严重超支，引擎在用"每帧多跑几次物理"来追赶：桌面 30 FPS 时每渲染帧实际要算 2–3 次物理 tick（Godot 默认 `max_physics_steps_per_frame` 上限 8）。于是：

- 每次物理变慢 → 帧变长 → 每帧塞进更多物理 tick → 帧更长。
- 这就是 p95 141 ms、max 396 ms 的尖刺来源，也是"看起来只有十几帧但某些帧几乎卡死"的原因。

**所以第一优先不是让某个函数快 20%，而是同时降低"每帧算几次"和"算一次多贵"。**

## 1.5 第二轮归因：真正的瓶颈是渲染提交，不是模拟（2026-11-17 追加）

P0 落地后又做了一轮归因，结论**推翻了原来的优先级**：

| 测量 | 结果 |
|---|---|
| 同一场景，**关渲染**（headless live，不封帧） | **13.69 ms/帧 / 73.1 FPS** |
| 同一场景，**开渲染**（后台 GPU 桌面） | **35.69 ms/帧 / 28.0 FPS** |
| 差值 | **渲染占了 22 ms，约 62% 的帧时间** |

再看渲染内部：
- 画布从 1920×1080 降到 1280×720、再降到 960×540（像素数降到 1/4），帧时间没有下降（31.4 / 28.2 / 34.2 ms，噪声内）。**所以不是填充率，是每个 draw call 的提交开销。**
- draw calls ≈ 850，而"关掉命中特效"（少 186 draws）省 5.4 ms → **约 29 µs/draw call**。按这个斜率，850 → 150 draws 可省约 20 ms。

同时按脚本实测（同一 12 秒窗口，28 FPS / 35.5 ms 帧）：

| 子系统 | ms/帧 | 占比 |
|---|---:|---:|
| 投射物（含扫掠 3.15） | 5.12 | 14% |
| 敌人（含 move_and_slide 0.59） | 2.91 | 8% |
| 赤铜炉灯 | 2.19 | 6% |
| 调度器回调 | 2.11 | 6% |
| 营地短刀 | 1.19 | 3% |
| 视觉特效脚本 `_process`（7 个已插桩） | 1.07 | 3% |
| **全部脚本合计** | **~14** | **39%** |
| **渲染（draw call 提交）** | **~22** | **62%** |

可见节点普查（1883 个可见 CanvasItem / 1986 总数，draw calls 850）：

| 节点类型 | 可见数 |
|---|---:|
| CollisionShape2D（不绘制，但占可见计数） | 497 |
| 守夜长枪碎片 `nightwatch_spear_shard` | 441 |
| 伤害数字 `combat_damage_number`（Label，每个一次 draw） | 160 |
| 像素火焰视觉 `pixel_fire_visual` | 159 |
| 火焰种子 `fire_seed` | 107 |
| MultiMeshInstance2D（已批处理） | 66 |
| 敌人本体 / 状态 / 地面阴影 | 48 / 48 / 48 |
| 闪电像素弓弧 / 闪电链 | 38 / 24 |

两个已验证的细节：
- 把长枪分裂碎片整体关掉只省 **3.24 ms / 9.6 draws**——那 441 个节点大部分是停驻/不绘制的，真正吃 draw 的是别的东西。
- 敌人自身只有 **2.91 ms/帧**，不是之前消融给出的 21.5 ms：`engine_physics_ms` 这个监视器在慢帧下不可靠（它把追赶的多次物理步叠加了），以脚本实测与 wall 为准。

### 因此优先级重排

1. **P3-渲染（draw call 提交）— 最大单块（22 ms，62%）**：目标 850 → <150 draws。
2. **P2 接触层（投射物扫掠 5.12 ms）**：物理查询换空间网格。
3. **P1 敌人（2.91 ms）**：优先级下调，收益远小于原估计。
4. P4 视觉回调归并（1.07 ms 已插桩部分）：优先级下调。

### 第八轮：帧时间预算（已实施）

新增 [autoloads/performance_budget.gd](autoloads/performance_budget.gd)（autoload 名 `PerformanceBudget`）：

- 每帧用真实 wall 时钟取一次帧间隔，维护 30 帧滚动窗口，每 0.2 s 求一次 p90；
- 三档：p90 ≤ 20 ms → `FULL(2)`；20–30 ms → `REDUCED(1)`；> 30 ms → `MINIMAL(0)`；
- 升档需要 p90 ≤ 17 ms（迟滞），档位切换有 0.8 s 冷却，> 250 ms 的卡顿样本（加载/切窗口）直接丢弃；
- 命令行 `--budget-tier=0|1|2` 可强制档位，用于 A/B 测量。

降级内容（**都不改伤害**）：

| 档位 | 伤害数字上限（普通 / 暴击） | 装饰视觉准入 | 扫掠频率 |
|---|---|---|---|
| FULL(2) | 128 / 160 | 原规则 | 每 tick |
| REDUCED(1) | 72 / 96 | 收紧一级（`claim_visual` 返回档 +1） | 每 2 tick |
| MINIMAL(0) | 36 / 48 | 收紧两级 | 每 2 tick |

实现点：
- `EnemyController._damage_number_limit()`：只改准入，**对象池仍是 160**，所以 `combat_hitch_regression_test` 的池断言与 `damage_number_animator_test` 的 128/32 分配都不受影响（均通过）。
- `EffectVisualBudget.claim_visual()`：把全局档位折算成 `admission_shift()` 加到本地档位上，一行接入就覆盖火焰/闪电/火花等所有装饰族。
- `ProjectileInstance._physics_process()`：积攒 `_sweep_accumulator`，按 `PerformanceBudget.sweep_period()` 决定何时扫掠。扫掠本身是**连续形状查询**，跨两个 tick 的更长矩形覆盖的正是同一段路程，命中不丢，只有命中时刻被量化到 ≤1 个物理 tick。

实测（手机配置 30 Hz/1 步、七武器压力场景、同种子、每档 2 次）：

| 档位 | FPS | 帧时间 | p95 | p99 | draw calls | damage_calls | impacts |
|---|---:|---:|---:|---:|---:|---:|---:|
| FULL(2) | 44.09 | 22.68 ms | 48.8 | 82.0 | 842 | 30,013 | 15,640 |
| REDUCED(1) | 49.56 | **20.18 ms** | 42.2 | 70.7 | 590 | 30,093 | 15,679 |
| MINIMAL(0) | 51.21 | **19.53 ms** | 40.4 | 63.2 | 410 | 30,651 | 15,916 |

拆分归因（同档位下把扫掠频率强制回 1）：

| 配置 | 帧时间 | 结论 |
|---|---:|---|
| FULL | 22.68 ms | 基线 |
| REDUCED 仅视觉降级 | 21.33 ms | 视觉上限值 −1.35 ms |
| REDUCED 视觉+扫掠降频 | 20.18 ms | 扫掠降频再值 −1.15 ms |

- 伤害侧：`damage_calls` / `weapon_impacts` 在 REDUCED 下变动 +0.3%/+0.3%，MINIMAL 下 +2.1%/+1.8%，都在该夹具自身的运行间波动范围内（FULL 档两次运行本身就有 30013 vs 29692 的差异）。
- 曾试过 MINIMAL 用"每 3 tick 扫一次"，伤害计数漂移约 +5%，收益只有 0.9 ms，因此**封顶在 2**，不提供 3。

按 2.5–4.5 倍真机倍率折算：FULL 22.7 ms ≈ 真机 10–18 FPS；MINIMAL 19.5 ms ≈ 真机 **11–20 FPS**。这部分收益在真机上会随帧时间比例放大（因为压力越大、落档越早）。

### 第七轮：P2「接触层换空间网格」实测否掉

原计划是把投射物扫掠里的敌人宽阶段（物理 `intersect_shape`）换成已有的 `EnemyRegistry.candidates_in_radius` 网格，理由是之前测到"物理凸多边形查询 84–99 µs vs 网格 3–7 µs"。在实验室里对**同一批 sweep**同时跑两条路径做 A/B（22,695 / 27,440 次 sweep）：

| 变体 | 物理宽阶段 | 网格查询 | 每次 sweep 候选数（物理 / 网格） | 接触集合分歧 |
|---|---:|---:|---:|---:|
| 网格 margin 176px | 8.9 µs | 10.5 µs | 5.06 / **29.38** | 23 |
| 网格 margin 40px | 7.9 µs | 8.3 µs | 4.34 / **14.83** | 15 |

结论（三条都指向"不做"）：

1. **网格并不更快**：8–10 µs vs 8–9 µs，基本持平。
2. **网格返回的候选多 3–6 倍**（29 vs 5），而每个候选还要进 `body_entry_fraction`（约 7 µs）→ 换过去整体更慢。
3. **网格不是精确超集**：margin 40px 有 15 处分歧，margin 176px 仍有 23 处分歧；要保证不漏判必须把 margin 放到"格子 128 + 最大体型"级别，候选数只会更多。

所以投射物的 5.1 ms/帧**不在"找候选"上**：物理宽阶段只有 8 µs、只返回约 5 个候选；钱花在 5 × 7 µs 的精确几何（进入距离二分）、地形三次查询和 sweep 本身的机制开销上。要再降只能改"算什么"——减少同时存在的投射物/扫掠次数、或降低精确几何的精度要求，而不是换查询通道。

这也说明之前那条"物理查询 84–99 µs"只适用于**短刀那种 34 顶点大凸包**（35 个候选）；对投射物的薄矩形查询，物理宽阶段本来就又快又准。

### 第六轮：`plasma_ball_visual._draw` 异常点（已查清，改法需美术决策）

`_draw` 插桩显示等离子球的绘制回调是最贵的单项：**1.02 ms/帧**，单次 **158 µs**（其他绝大部分 `_draw` 是 2–6 µs）。原因查明：

- 该效果用"逐像素 `draw_rect`"画闪电：每个弧 8 段，每段按 `max(|dx|,|dy|)` 逐像素发 1px 方块 → 单弧约 40 条画布命令，最多 6 条弧 → **单次重绘约 240 条命令**，按兼容渲染器约 0.55 µs/命令 ≈ 130–160 µs，与实测吻合。
- 与 `_draw` 同为逐像素风格的其它效果（`PIXEL.line/path`）也用 2px 网格方块，但数量远小。

尝试并**已回退**的改法：对逐像素落点去重（相同像素只发一次，理论上像素级完全等价）。实测 158.3 → 160.6 µs/次，**无收益**——落点基本不重复，说明命令数就是像素数。

真正能砍下来的只有一条路：**把 1px 白色核心从"逐像素方块"改成单条 `draw_polyline`（约 40 条命令 → 1 条）**。这会把闪电核心从"阶梯像素"变成"连续 1px 线"，属于可见的美术变化，需要美术确认（项目有明确的像素阶梯风格要求），所以我不擅自改。

优先级判断：该项全部收益约 1 ms（占帧 4%），远小于 P2 的 5.1 ms，建议排在 P2 之后。

### 第五轮：`WORLD_RENDER_SIZE` 降档实测（否掉）

先验证"降内部分辨率能省时间"这个假设。关键是要确认**渲染目标真的变小了**（上一轮改窗口尺寸是无效的），所以在夹具里加了一条实测输出：

```text
px_1920x1080: RENDER_TARGET viewport=(1920,1080)  window=(1920,1071)
px_960x540 : RENDER_TARGET viewport=(960,540)    window=(960,540)
```

同场景、同种子、各跑一次实时采集：

| 配置 | 渲染目标 | FPS | wall | p95 | draws |
|---|---|---:|---:|---:|---:|
| 1920×1080 | 1920×1080 | 38.41 | 26.04 ms | 55.9 | 852 |
| 960×540（像素 1/4） | 960×540 | 38.45 | 26.01 ms | 56.1 | 837 |

**4 倍像素差，帧时间差 0.03 ms**。结论：在桌面显卡上这块内容的帧时间与填充率无关，**降内部分辨率不是杠杆**（`WORLD_RENDER_SIZE` 不必改）。

需要注意的边界：这是桌面 GPU。移动 GPU 的填充率弱得多，重叠加法发光在 1080p 上仍可能吃 GPU；但桌面 4 倍像素差零响应说明整帧是 CPU 端受限（852 draws + 1883 个运动节点），手机上降分辨率解决不了 CPU 侧那一半。

另：尝试把夹具包进 SubViewport 复刻生产渲染路径的实验失败了（包装后世界不渲染、模拟也不跑，draws 掉到 8），该数据不可用，已放弃该测量方式。生产代码里的 `WORLD_RENDER_SIZE` 因此**不改**。

### 第四轮：渲染成本模型已量化（合成探针，2026-11-17 追加）

为了把"固定开销"和"每项/每次 draw 的边际成本"分开，新增了合成探针
[scripts/tests/render_floor_probe.gd](scripts/tests/render_floor_probe.gd)（`--count/--mode/--move/--subviewport`），
在同一个后台 GPU 桌面上按不同节点数、是否运动、是否包 SubViewport 测量：

| 配置 | 提交对象 | draw | 帧时间 |
|---|---:|---:|---:|
| 0 个精灵 | 0 | 0 | 0.147 ms |
| 2000 静态（同纹理） | 594 | 1 | 0.457 ms |
| 4000 静态（同纹理） | 864 | 1 | 0.700 ms |
| 2000 静态（各不同纹理） | 594 | 594 | 3.476 ms |
| 864 静态（各不同纹理） | 864 | 864 | 5.373 ms |
| **2000 运动**（同纹理） | 596 | 1 | **2.563 ms** |
| **2000 运动**（各不同纹理） | 596 | 596 | **5.800 ms** |
| **867 运动**（各不同纹理） | 867 | 867 | **9.123 ms** |
| 2000 静态 + SubViewport | 595 | 2 | 0.851 ms |

拟合出的成本模型（本机 GL Compatibility）：

```text
渲染 = 0.64 µs × 静态节点 + 约 4 µs × 每帧运动的节点 + 5.4 µs × draw call
       + 约 0.4 ms（SubViewport 固定开销）
```

三条结论：

1. **不存在"~10 ms 固定渲染开销"**。空场景只有 0.147 ms，SubViewport 只加 0.4 ms。之前那个"固定 10 ms"的推断来自"关渲染 vs 开渲染"的差值，而 headless 会同时跳过 `_draw()` 与画布命令构建，把差值算大了。
2. **运动的节点比静态贵约 6 倍**（0.64 → 约 4 µs），draw 的边际成本是 5.4 µs。本场景约 1883 个可见节点几乎都在动、843 次 draw，据此推算渲染 ≈ 843×5.4 µs + 1883×4 µs ≈ 12 ms，与实测的 13–22 ms 量级吻合。
3. **之前"降分辨率无收益"的测试是无效的**：真实战斗渲染在固定 1920×1080 的 `SubViewport`（`WORLD_RENDER_SIZE` 常量，`transparent_bg`）里，改项目窗口的 viewport 尺寸并没有改变世界渲染目标。**手机端要降填充率，必须改 `WORLD_RENDER_SIZE`**，这条杠杆至今没被测过，在移动 GPU 上可能是数毫秒级。

按此模型，各批处理目标的真实收益（本场景）：

| 目标 | 现状 | 可省 |
|---|---|---|
| 伤害数字（160 Label，601 draw + 文本逻辑） | 实测 −3.0 ms | ~3 ms |
| 火焰视觉/种子 266 节点 | 约 266×4 µs + 少量 draw | ~1.5 ms |
| 敌人本体/状态/阴影 144 节点 | 144×4 µs | ~0.6 ms |
| 长枪碎片红绘（已做） | 已省约 2.3 ms | 已完成 |
| **合计** | | **约 7 ms**（26.6 → 约 19 ms） |

也就是说：把渲染侧全部做完，桌面从 26.6 ms 降到约 19 ms（52 FPS），**仍然不够** 让手机到 30 FPS——还必须同时把 13.7 ms 的模拟成本砍掉一半（投射物 5.1 + 炉灯 2.2 + 敌人 2.9 + 调度 2.1 + 短刀 1.2）。这是两个独立的、各需数周的工作块。


在动手改渲染之前先做了一次针对性验证——把伤害数字（160 个 `Label`）整体关掉：

| 配置 | FPS | wall | p95 | draw calls |
|---|---:|---:|---:|---:|
| 伤害数字开 | 37.92 | 26.37 ms | 58.3 | **842.9** |
| 伤害数字关 | 42.80 | 23.37 ms | 54.3 | **241.5** |

- **160 个 `Label` 实际吃掉 601 次 draw（约 3.75 次/个）**：每个伤害档位一个主题，材质状态不同，画布批处理被切断。
- 但这 601 次 draw 只换来 **3.0 ms**（26.37 → 23.37），即 **draw 的边际成本约 5 µs**，不是之前用"关命中特效"估出来的 29 µs（那次同时删掉了几百个特效节点，把节点开销算进了 draw 成本）。

修正后的渲染成本模型：

```text
渲染总开销 ≈ 固定开销(~10 ms，与 draw 数几乎无关) + draw 数 × 5 µs + 可见节点数 × 约 19 µs
```

- 843 draws → 渲染约 13 ms；241 draws → 约 9.7 ms。
- 所以"850 → 150 draws 省 20 ms"的推算**是错的**；真实收益约 3.5 ms（draw）＋节点合并的额外部分。
- 现在最大的未知项是那 **~10 ms 的固定渲染开销**：它与分辨率无关、与 draw 数关系不大，嫌疑是 1883 个可见 CanvasItem 的剔除/排序/命令构建，或 SubViewport 的固定成本。

### 因此当前的正确动作

1. **先测渲染地板**：空场景 / 只放 50 个 CanvasItem 的同场景，测出固定开销的真实值，再决定是削节点数还是查 SubViewport。
2. 伤害数字批处理（601 → 约 3 draws）**仍值得做**（约 3 ms，占帧 11%），但要按"合并节点"而不是"少画"来做，并且会牵动 6 个断言 `child is Label` 的测试。
3. 在这个固定开销查清之前，不再按"省 draw 数 × 29 µs"估算收益。

### P3 的具体落地顺序（每步都用 draws / wall 验证）

1. **伤害数字合并节点**：160 个 `Label` 实测占 601 次 draw（每档伤害主题不同，批处理被切断），换成单个 CanvasItem 用 `draw_string` 批量绘制（保留现有池、预算与动画状态机），目标 601 → 约 3 draws，约 −3 ms。
2. **火焰视觉/种子批量**：`pixel_fire_visual` 已有共享 `clock.batches`，但 `_flush_local()` 仍为每个 actor 局部实例单独建 `_local_batch`；改为共用批次需先确认渲染层次语义（`layer=25` 由 `set_effect_layer` 决定，与"作为敌人子节点"的深度不同），属于视觉顺序变更，需要评审。
3. **敌人视觉三件套**：阴影按 `(kind, footprint, air_step)` 生成不同纹理，无法直接并批；需要先做图集化。
4. **红绘纪律（已做第一处）**：`nightwatch_spear_shard` 之前每个 tick 无条件 `queue_redraw()`，而它的 `_draw` 只依赖开局确定的方向与染色。改为仅在 `direction` 变化时重绘（`_painted_direction`）。实测中位数 40.18 → 37.89 ms（−2.3 ms），与"整体关掉全部碎片只省 3.24 ms"的独立消融吻合；但 3 次采样噪声 ±2 ms，因此按"资源使用正确性"而非"已证实的提速"记录。

修正后的预期：draw 边际 5 µs，850 → 240 约省 3 ms；节点数合并每项约 19 µs。要真正拿到 10 ms 以上，必须先查清那 ~10 ms 的固定渲染开销。

## 2. 第一轮消融记录（结论已被 1.5 节修正，保留备查）


用命令行开关逐个子系统关闭，各跑一次同样的 12 秒实时采集（`--ablate-*`）：

| 配置 | FPS | wall | process | physics | draws |
|---|---:|---:|---:|---:|---:|
| 基线 | 29.95 | 33.39 | 20.25 | 45.50 | 809 |
| 关闭命中后附魔事件链 | 35.70 | 28.01 | 8.32 | 46.73 | 623 |
| 关闭敌人 AI/移动 | 39.70 | 25.19 | 32.83 | 23.99 | 874 |

由此得到两条结论（**第 1 条已被 1.5 节的脚本实测推翻**）：

1. ~~敌人 AI + 物理体移动约占 21.5 ms/帧~~ → 实测敌人脚本仅 **2.91 ms/帧**。21.5 是 `engine_physics_ms` 在慢帧下叠加多次物理步造成的假象。
2. **命中后事件链连同它生成的视觉节点约占 5.4 ms wall、186 个 draw calls**（这条被后续测量支持）。

（另有两次消融无效：关闭投射物/定向武器会让节点永不销毁而堆积，数据不可用，已排除。）

分层看基线 33 ms（第一轮估计，**已被 1.5 节的实测取代**，保留作为当时的推断记录）：

| 层 | 约计 | 说明 |
|---|---:|---|
| 敌人 AI / 移动物理 | 21.5 ms（实测仅 2.9 ms） | 第一轮把物理监视器的差值算成了敌人开销 |
| 投射物扫掠 + 武器接触 | ~10 ms（实测 5.1 + 2.2） | 34 个投射物 × 60 Hz |
| 命中后事件链 + 其特效节点 | 5.4–12 ms（实测 5.4） | 约 1000 次命中/秒 |
| 渲染（draw call 提交） | 首轮未测 | 实测 22 ms，62% |
| draw calls | 809 | 手机 GL 上会直接成为瓶颈 |

## 3. 方案：五根支柱

顺序按"收益 ÷ 风险"，每根都能独立验证、独立回滚。

### P0 帧预算架构（已实施，实测 1.45x–1.66x）

已落地两处改动：

1. `project.godot` → `[physics] common/max_physics_steps_per_frame=2`：禁止"每帧补算最多 8 次物理"的追赶循环。
2. `autoloads/mobile_profile.gd` → `apply_simulation_budget()`：手机端物理 tick 30 Hz、最多 1 步；桌面保持项目原 tick，只封顶 2 步。

实测（真实项目、后台 GPU 桌面、七武器压力场景、12 秒实时采集、每组 2 次取均值）：

| 配置 | FPS | wall | p95 | p99 | max |
|---|---:|---:|---:|---:|---:|
| 改动前（60 Hz，最多 8 步） | 21.92 | 45.62 ms | 178.6 | 307.3 | 367.4 |
| 改动后 · 桌面路径（60 Hz / 2 步） | 31.68 | 31.69 ms | 78.6 | 114.3 | 135.3 |
| 改动后 · 手机路径（30 Hz / 1 步） | 36.43 | 27.45 ms | 62.0 | 101.0 | 262.9 |

- 桌面路径：**+44.5% FPS，wall −30.5%，p95 −56%，p99 −63%，max −63%**。
- 手机路径：**+66.2% FPS，wall −39.8%，p95 −65%，p99 −67%**。

按 3–4 倍真机倍率换算，同一场景从 5.5–7.3 FPS 提升到 9.1–12.1 FPS。**这只是 3–6 倍差距里的大约 1.6 倍**，剩下的必须靠 P1–P5。

已验证：`mobile_profile_test` 26/26；`contact_query_interior_test` 9618/0；`continuous_contact_test` 3349 项中 3 项失败、`camp_dagger_test` 77 项中 21 项失败、`mobile_bank_test` 41 项中 1 项失败——均为改动前后逐条一致的既有失败（已用暂存对照确认）。

### P0 原计划的其余三项（未实施，仍建议做）

1. **每帧时间预算**：调度器与特效生成改为"本帧预算 4 ms，未完成队列顺延"，进一步压 p95/p99。目前 max 仍有 135–263 ms 的尖刺。
2. **离屏剔除**：屏幕外敌人/特效跳过 `_process`/`_physics_process`。测试夹具里敌人都在屏内，测不出收益，需要真实关卡数据。
3. 视觉插值（`physics/common/physics_interpolation`）：30 Hz 下让移动更顺滑，实测额外花 3 ms/帧（40.8 vs 46.4 FPS），是否值得由手感评审决定。


### P1 敌人单位成本（最大单块，预期 5–7x：21.5 → 3–4 ms）

1. AI/索敌 30 Hz（与 P0 联动），寻路方向按 30 Hz 重算。
2. **敌人不再用 `move_and_slide`**：改为脚本积分位置 + 用现有 `EnemyRegistry` 空间网格做分离/避障（网格查询 3–7 µs，`move_and_slide` 每敌数百 µs）。
3. 敌人物理体只保留被玩家/投射物命中的形状，去掉敌人之间的物理碰撞（用网格做软分离）。
4. 目标：48 敌人从 21.5 ms → 3–4 ms。

### P2 接触层：物理查询换空间网格（预期 10 → 2–3 ms）

1. 投射物扫掠改为：网格取候选（3–7 µs）→ 沿射线的 AABB 进入距离作下界排序 → 只对最靠前的候选做精确 `Shape2D.collide`，找到第一个真实接触即停（可证明等价于"取最早接触"，不需要对所有候选跑 14 次二分）。
2. 同一套替换炉灯锥形、长枪、战锤、连枷、电浆的接触扫描（它们目前各自发物理查询）。
3. 保留现有精确几何（`.collide`），不改命中判定，只改"找候选"的方式，便于用现有 9618 项接触测试与 3349 项连续接触测试守护。
4. 目标：单次扫掠 130 µs → 20 µs。

### P3 命中链与特效（预期 12 → 3 ms，draw calls 809 → <150）

1. 参数上下文按 (武器, 附件) 缓存，用便宜信号失效（目前每次生成要重读 4 个属性并深比较附件）。
2. 特效生成合并：短命特效由一个批处理节点绘制（图集 + 单 CanvasItem），不再每个特效一个节点 + 一个材质。
3. 每帧生成上限与聚合：同一位置同一元素的多个特效合并，纯装饰部分按设备档位降级。
4. draw calls 目标是 **<150**，这是手机 GL 的生死线。

### P4 每帧脚本回调归并（预期 8 → 3 ms）

1. 目前约 250–300 个视觉节点各自 `_process`（地面阴影 48/帧、受击受光 45/帧、火焰种子 46/帧…）。改为一个管理器遍历数组更新，省掉对象/调用开销。
2. 静态/停驻节点 `set_process(false)`。

### P5 自适应质量与真机验证（保证"稳定"）

1. 内部分辨率缩放（像素画本来就该这样）：手机按帧时间在 0.5–1.0 之间动态调整，像素数可省 4 倍。
2. 设备分档：低端机降低同屏敌人上限、特效预算、关闭部分装饰层。
3. 游戏内轻量 profiler 覆盖层（FPS / 帧 ms / draw calls / 对象数 / 活跃特效数），供真机回传。

## 4. 验证口径（缺这个就谈不上"稳定"）

建一个"手机等价"基准：

- 固定内部分辨率、固定物理速率、固定种子；两档敌人密度（48 / 96）；七武器压力配置。
- 每档输出：`wall` p50/p95/p99/max、`process`、`physics`、draw calls、节点数、每帧命中数。
- 每根支柱单独 A/B，**要求 p95 不回退**，不接受"平均变快但尖刺更差"。
- 验收线：桌面同场景 ≥100 FPS 且 p99 ≤ 20 ms；真机 ≥30 FPS 且 1% low ≥25。

## 5. 里程碑与预期

| 里程碑 | 内容 | 桌面预期 | 手机推算 |
|---|---|---:|---:|
| M1 ✅ | P0 帧预算（已实施实测） | 21.9 → 31.7 / 36.4 FPS | 5.5–7.3 → 9.1–12.1 |
| M2 | P1 敌人单位成本 | 36 → 55 FPS | 12 → 18 |
| M3 | P2 接触层 | 55 → 70 FPS | 18 → 23 |
| M4 | P3 命中链 + 渲染批处理 | 70 → 90 FPS，draws < 150 | 23 → 30 |
| M5 | P4 + P5 自适应质量 | 100+ FPS，锁定上限 | 稳定 30 |

## 6. 明确不建议的做法

1. **继续按武器做 5–10% 的微优化**。已实测：短刀接触降 30% 只换来整帧 ~5%；附魔链与投射物候选二分两处试改，一处收益 1%、一处为零（已回退）。单点优化无法跨越 3–6 倍差距。
2. **只看桌面帧率就宣布解决**。手机 5–10 FPS 必须真机复现：需要机型、实际游戏版本、波次/侵蚀度、七把武器的附魔组合、同屏怪物数。
3. **靠减小特效数量硬撑**。P3 的合并与 P5 的分辨率缩放是"同样的观感更便宜"，而直接砍特效会改变战斗可读性——本项目已有多轮 VFX 美术基准，砍视觉要单独评审。

## 7. 需要用户确认的两件事

1. **真机信息**：机型 / 系统 / 出现 5–10 FPS 时的具体配置（波次、侵蚀度、同屏敌人数、七武器附魔、是否开了分裂+火焰+闪电）。没有这些，桌面上的"最坏情况"只能靠猜。
2. **是否接入游戏内 profiler 覆盖层**：这是把"真机 5–10 FPS"变成可归因数据的唯一低成本手段，也是后续每一步能否宣称"真的变快了"的判据。
