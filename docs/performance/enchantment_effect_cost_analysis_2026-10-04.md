# 当前单附魔与组合附魔的特效性能分析

分析对象为 2026-10-04 当前正式实现，包括已安装的 2px 缓存雷电、合批像素火焰、组合特效简化和草簇合批。本轮只新增诊断脚本及报告，未修改正式法术和美术资源。

**主要判断**

不能用左上角的粒子数给所有附魔排序。当前最需要处理的是三类不同开销：水波、冰霜、反射等像素图形的脚本绘制；雷火爆炸与落雷命中散粒的 CPU 更新和实例提交；反射、连锁选敌、落雷和大量伤害数字的战斗逻辑开销。独立微测中水波的 CPU 绘图尤其突出。普通火焰和主闪电路径已完成一轮有效优化，不宜再次从删掉其外观入手。

这里的“优先级”是由代码结构、扩张风险和诊断证据共同确定的工程优先级，不是所有武器、敌人数量与触发频率下固定不变的 FPS 排名。

**本次分项实测**

Godot 4.7.2，Compatibility／ANGLE，Intel Arc 集成显卡，1152×648，独立微测设置 60fps 上限，不读取截图。下表直接计时正式绘图方法的 CPU 工作，包含像素图形准备和引擎调用，不包含完整 GPU 执行，也不包含敌人、伤害和状态查询。每项预热 1 秒、测量 4 秒，细节固定为最高档；密集实战会采用已有自动细节档，因此不应将这里的 8 实例结果线性外推所有战斗。

| 原样绘制对象 | 1 实例 CPU 绘图／帧 | 8 实例 CPU 绘图／帧 | 说明 |
| --- | ---: | ---: | --- |
| 水波 | 2.47ms | 14.93ms | 每帧重建轮廓、像素填充和泡沫；8 实例整帧平均 17.72ms，P95 21.79ms |
| 冰光反射光线 | 0.89ms | 5.70ms | 不含逐帧扫描敌人和伤害结算 |
| 冰场结晶 | 0.42ms | 3.09ms | 保留正式 12fps 重画；单次重画约 1.9–2.1ms，表中为分摊至显示帧的平均值 |

8 个冰场并非每帧都各重建一次；不同步重画有较低平均值，同帧生长／扩展仍可能产生尖峰。水波与反射的实例相位不同，CPU 缓存和负载也不同，1 与 8 实例数据不是严格线性关系。

粒子微测保留正式 `explosion_burst`，每秒 10／30 次发射各反向顺序重复两次，每次预热 2 秒、测量 4 秒。以下为两轮平均值：

| 发射频率 | 平均存活粒子／绘制实例 | 运动模拟 CPU／帧 | 绘制准备 CPU／帧 | 发射准备 CPU／帧 |
| --- | ---: | ---: | ---: | ---: |
| 无发射 | 0／0 | 0.029ms | 0.013ms | 0ms |
| 10 次／秒 | 290／579 | 0.171ms | 1.307ms | 0.129ms |
| 30 次／秒 | 828／1,655 | 0.376ms | 4.211ms | 0.355ms |

在这组发射时序下，粒子绘制准备明显重于运动模拟。60fps 整帧预算仅 16.67ms，约 828 粒子的绘制准备已占约四分之一；不能把这些 CPU 时间解释为 GPU 渲染时间，也不能承诺优化后能回收全部开销。

120 怪受控场景完成 21 种单元素／组合情况、共 42 次测量。采样实际观察到：火 + 落雷触及单个粒子世界的 900 上限；冰光反射同时达到 36 条；冻结提示达到 36 个；蒸汽提示达到 60 个；多个场景达到 128 个普通伤害数字。峰值是采样观测值，不保证捕获每一帧的真实最大值。它们说明“每次看起来很少”的图形会因目标数成倍增加。

整场测量期间另有 Godot 录制并发使用 GPU，整场 FPS 仅保留在原始结果中，不用于严格排行。之后的独立微测开始时及过程中检查，仅保留现有编辑器与本次测试引擎；未发现其他测试引擎。绘图类微测各一次、采样较短，应视作定位证据，不能据此承诺特定帧率收益。

**单附魔：开销来自哪里**

| 单附魔 | 当前主要成本 | 优化优先级与判断 |
| --- | --- | --- |
| 电火花／落雷 | 落点散粒一次，范围内每个实际受伤目标还生成一次命中散粒；另有光晕、主雷电及目标查询 | 高。密集怪群下，同一次落雷的成本随受击目标增加，主路径并非唯一来源 |
| 爆破／震荡（内部 ID `explosion`） | 默认每次 96 个方块粒子，附带光晕；当前单附魔逻辑是推开，雷火反应另走伤害分支 | 高触发频率时优先。最适合试做保持轨迹、颜色和数量的解析运动批次 |
| 冰 | 冰场结晶、生长及渐隐；大量敌人脚下的减速霜纹；冰场每 0.12 秒碰撞查询 | 高。冰场已限制 12fps 重画，但其生成和静态状态图案仍可优化 |
| 水 | 每帧生成 3 组 96 点轮廓、多层像素填充、波沿、泡沫与内侧波纹 | 最高优先级之一。独立微测确认 CPU 绘图开销高，粒子数却可以为 0 |
| 黑洞 | 球体、吸积环、吸入短线和阴影每帧重画；逐帧移动已收集的目标 | 中高。绘制和聚怪／位移要分开衡量，不能全部归因于粒子 |
| 光剑 | 56 行剑体色块每帧重画，叠加落地及裂痕；范围伤害与状态标记 | 中。多个光剑同时存在时适合缓存剑体和裂痕 |
| 闪电链 | 主路径已一次生成网格；每次命中仍有散粒、光晕，跳转查找扫描敌人 | 常规中，分裂、多投射物、高跳数时高。不要重新采用沿路径生成粒子的方式 |
| 火 | 共享着色器／MultiMesh、燃烧实例、火场光照、持续伤害与数字 | 当前视觉优化优先级中。大面积重叠、许多燃烧目标时仍需关注像素填充与战斗结算 |
| 风 | 风刃轮廓较简单；飞行过程中每帧遍历敌人检查命中 | 粒子优先级低，查询成本在多风刃、多怪场景会升高 |

**组合附魔：额外成本与继承成本**

| 组合 | 应重点关注的部分 | 判断 |
| --- | --- | --- |
| 火 + 闪电链／落雷：雷火爆炸 | 每个被引爆的燃烧目标都可能生成 96 粒子爆炸，并做范围伤害；同时还有原雷电散粒 | 最高优先级之一。密集目标、反复点燃、分裂多投射物会放大发射次数 |
| 水 + 冰 + 光剑：冰光反射 | 冻结外壳、冰场、光剑和反射同时存在；每条反射每帧扫描敌人、逐像素绘制多层长光线 | 最高优先级之一，但主要不是传统粒子。须保留每轮冻结的触发次数及扫射命中时序 |
| 水 + 冰：冻结／解冻 | 入场冰晶、静态冰壳、解冻碎片、冰场；大量目标同时冻结会集中生成图形 | 高性价比优化对象，静态冰壳最适合按变化缓存 |
| 风 + 冰：冰晶扩展 | 冰场扩大、更多霜纹和覆盖目标，另有短时扩展前沿 | 中高。扩大半径会增加路径像素数和查询范围，不能只数冰场个数 |
| 水 + 闪电链／落雷：感电 | 接受过的短蓝电弧已经很轻；额外命中、原雷电和数字仍有成本 | 不优先削弱短电弧。先处理原落雷／命中散粒与伤害显示 |
| 火 + 水／水 + 火：蒸汽 | 每个触发目标生成 2–3 朵多边形烟团，每帧重建；火场可能重新点燃，使反应反复出现 | 大批怪物反复触发时中高；常规单次中等 |
| 火 + 光剑：圣焰 | 使用已有火焰批次，仅调色；持续伤害变化和光剑本体成本仍在 | 转色本身低，不再有旧冠状星光和额外火舌 |
| 火 + 黑洞：暗焰 | 使用已有火焰批次；燃烧可延长到 10 秒，黑洞聚怪使覆盖与重叠增加 | 转色本身低；总成本可能因同时燃烧人数和持续时间增加 |
| 暗焰 + 水 | 蒸汽出现，暗焰保留，可继续重复触发 | 关注蒸汽产生频率及数字，不需要重新增加暗焰特效 |
| 风 + 火 | 扩大已有火场与覆盖目标；保留三火舌组合 | 关注覆盖面积、持续伤害与光照，没有独立风火爆炸 |
| 水 + 风 | 一条较淡短水带，默认最多传播至 4 个目标；传播可继续触发冻结／蒸汽 | 水带本身低，后续反应次数可能更重要 |
| 光剑 + 黑洞：光暗抵消 | 已无新增抵消图形，只清标记 | 抵消特效成本近零；两个基础法术的成本仍在 |

火 + 冰目前没有独立融化特效；黑洞与水、冰、雷多为聚怪带来的间接相互作用。分裂、弹射和投射物数量是触发次数的放大器，不能把一次命中的成本直接当作整套构筑的成本。

**粒子计数的具体含义**

- `particle_world.gd` 的 `explosion_burst` 默认 96 粒子，寿命 0.24–0.38 秒。默认无重力、阻力和旋转，因此适合一次记录初始参数，用时间直接计算运动。
- 雷电每次 `_emit_hit_burst()` 默认发射 5 个 `lightning_flash` 和 30 个 `lightning_impact`，共 35 个；实际数量还会受属性倍率影响。落雷既在落点发射，也对实际受伤的每个敌人发射，不能按“一次落雷只有 35 粒子”估算。
- 冰场调用 `ice_burst` 时使用 `0.6 × 0.3` 的数量倍率，默认约 13 个，不能把配置中的 72 当成当前每次冰场实际数量。
- 爆炸和雷电粒子都附带光晕。一个逻辑粒子通常占两个 MultiMesh 实例。900 个带光晕粒子可达到 1,800 个实例，每实例仍逐个设置变换、颜色和自定义数据，约 5,400 次 setter／帧；合批不等于 CPU 更新免费。
- 粒子每帧经过模拟与绘制准备两轮遍历，过期时 `_particle_order.remove_at()` 会移动后续元素。已有空闲槽池，但这部分仍可改为保持顺序的压缩。
- 900 是每个 `ParticleWorld` 的容量。通常会找到共享战斗世界，但不应据此断言整个进程永远只有 900 粒子。
- HUD 的 `combat_particle_counters` 不完整覆盖火焰着色器、状态冰壳、水波、反射、反应提示、伤害数字和光照。像素方块绘制调用也不等于逐块产生一个 GPU draw call，Godot 仍可能合批。

一个量级示例：每秒 10 次默认爆炸，平均寿命约 0.31 秒，对应约 `10 × 96 × 0.31 ≈ 298` 个同时存活粒子；每秒 30 次接近 893，已经接近单世界上限。高负载下数量被截断，会掩盖原本更高的发射需求。

**建议的实施顺序**

1. **先消除不必要的 CPU 工作，保持视觉。**
   - 状态缓存继续向绘图侧推进：`enemy_status_visual.gd` 已缓存状态查询，但当前冰壳、减速霜纹、小图标绘图不使用时间，仍被 12fps 定时重画。只在状态掩码、体型和外观参数变化时重画；移动由节点变换承担，火焰由共享时钟继续驱动。
   - 粒子 MultiMesh 改为复用连续 buffer 并批量提交，保留每粒子的光晕→主体顺序和所有颜色、大小、渐隐参数。已有槽池继续复用；死亡列表做稳定压缩，避免频繁删除和移动数组元素。
   - 复用上下文解析结果、查询对象和临时数组。伤害数字使用对象池，保持每次最终数值、飘字位置和时序；不把合并数字当成无视觉变化的优化。

2. **对复杂像素图形缓存几何，避免每帧从像素规则重新解释。**
   - 冰壳、减速霜纹、小图标优先共享网格／纹理缓存，以体型、状态、细节档为键，并限制缓存容量。
   - 冰场保持当前 12fps 生长与消退节奏，缓存对应阶段的几何；透明度单独调制。半径或扩展状态改变时才失效。不能直接无限缓存任意浮点半径。
   - 水波优先复用三角函数采样、数组与栅格化缓冲，并合并相邻同色行段；进一步尝试缓存网格或低分辨率着色器。水的轮廓随时间变化，改成少帧贴图或降低重画频率可能改变运动感，需要单独审阅。
   - 反射保持当前像素网格和扫射角度，改为批量几何生成／提交。简单旋转一张像素贴图可能产生斜像素、模糊，不能未经比对就宣称视觉完全一致。
   - 光剑缓存剑体行段与裂痕；黑洞缓存静态形状、复用动态缓冲。保留遮挡、收缩、消散与前后环的绘制顺序。

3. **单独优化爆炸与雷电命中散粒。**
   - 第一候选是 96 粒子的爆炸：保留每粒子的随机初始参数、寿命、速度、像素取整、光晕和透明度曲线，用着色器按时间计算位置，CPU 只负责发射和回收批次。
   - 验证爆炸后，再处理雷电命中散粒。雷电部分粒子有重力／阻力，不能直接套用匀速爆炸公式；须保持现有轨迹和分布。
   - 主雷电已采用一次构建网格，继续保留独立初始／闪回路径和 100%→60%→消失。高并发时可研究缓冲复用和发射端成本；不把重新降低像素精度作为首选。

4. **再处理与粒子无关的查询放大。**
   - 给敌人、火场、冰场维护空间网格，用局部候选集服务闪电跳转、风刃、湿润传播和反射扫描。
   - 保留现有距离／碰撞判定、目标顺序、随机分布与 RNG 调用约定；风的“前几个目标”和雷电的“最远／随机目标”不能因容器顺序变化悄悄改变。
   - 落雷当前用全敌人遍历补偿物理世界尚未同步的新生对象，再做物理查询。可把补偿缩到未同步对象集合，而不是直接删掉补偿。
   - 不降低伤害更新频率，不跳过画外伤害，不减少连锁命中次数；这些会改变玩法。

5. **最后依据 GPU 证据处理重叠和着色器。**
   - 火焰已经使用共享材质、批次和实例缓存。下一步是屏幕范围裁剪、批次边界以及大片透明区域，而不是继续删火舌。
   - `is_visible_in_tree()` 不等于在摄像机视野内；屏幕外剔除必须覆盖火舌、火星和光晕的最大边界，入镜时保持原动画相位。画外战斗计时继续运行。
   - 火焰动画虽然量化到 18fps，片元着色器仍随屏幕渲染帧执行；两次噪声采样、三角函数和火星判断不会因此只算 18 次／秒。
   - 光照圆盘几何已经缓存，可再评估实例合批与重叠填充。当前图形后端的 GPU 计时曾返回 0，不能把它当成 GPU 无开销。

**哪些措施需要再次审阅外观**

减少 96 粒子数量、合并多个爆炸成一个、缩短或减弱感电、删光晕、降低动画帧率、把多种随机路径改成同一张贴图，都可能改变已接受的表现。以上不应混入“保持视觉的优化”默认实施。降低伤害频率、减少目标数、缩短场地持续时间则是玩法修改。

**验证与测量边界**

本次增加 120 个真实敌人的固定场景，每秒两轮元素接触，单元素每轮一个法术，组合按 0.1 秒间隔施放前置与触发法术。使用正式 `CombatEffectWorld.trigger_weapon_impact`，敌人保留状态、碰撞和击退，禁用主动追逐；每项预热 3 秒、测量 4 秒，两轮反向顺序运行。未截屏读回，1152×648、关闭垂直同步与帧率上限。

它是受控触发压力检查，并非满级木弓 +3 投射物的完整战斗复测，也不覆盖所有组合顺序。不同法术会改变聚怪、击退、存留状态和伤害数字，帧时间差不能全算作特效成本。测试期间检测到其他线程的 Godot 录制并发占用 GPU，因此整场 FPS 不作为严格排序或可承诺收益；原始数据保留供复核。

粒子与绘制微测另用诊断子类包裹正式方法计时，统一设置 60fps 上限以比较每帧 CPU 预算：粒子保留原模拟、发射和绘制准备；水、冰、反射保留正式 `_draw()`，仅用动画时钟驱动，隔离掉伤害和查询。CPU 方法耗时不包括完整 GPU 执行，也不能直接相加推导实战 FPS。

复测标准应同时覆盖：相同种子、装备、敌人、摄像机与触发时间下的画面；伤害总量、命中顺序、状态时长；不录像时的平均帧耗时、P95／P99；实际粒子实例、火舌、光源、反射和伤害数字峰值。先测 120、300 怪，再补此前 1,000 怪、满级木弓、+3 投射物、分裂 + 闪电链的极限场景。画面审阅录制与性能测量分开进行。
