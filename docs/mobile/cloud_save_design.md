# 移动端账号云存档方案

日期：2026-11-08。状态：设计方案，尚未接入后端或部署。

## 目标和边界

玩家不选择文件夹、不手动导入导出。正常完成 TapTap 登录后自动同步天赋进度；卸载重装后登录同一账号自动恢复。

恢复范围包括天赋点、已购买天赋、建筑解锁、结算凭据和必要的存档版本信息。音量等设备设置留在本机。隐私同意、SDK 登录凭据和实名认证结果不属于游戏存档；重装后仍需要按现有流程同意隐私政策和登录。

只有服务端确认收到的进度能保证跨卸载恢复。离线期间尚未上传的进度无法在删除应用后找回。界面在设置中显示“已同步／待同步／同步失败”，不弹出目录选择流程；结算页明确区分“已保存到本机”和“已同步到云端”。

## 推荐部署

采用一个小型 HTTPS API 加托管 PostgreSQL。客户端不直接写数据库。首版只需要账号认证、读取存档和提交进度三个能力；不必搭建完整游戏服务器。

可以使用云函数或常驻轻量服务托管 API。上线前需选定服务商、区域、预算及域名，并核对 TapTap 当前官方登录凭证的服务端验证接口和账号标识作用域。当前 SDK 只有登录和合规接入，不能假设已经具备可用的云存档服务。

服务端用验证后的 TapTap 应用内账号标识关联内部 player_id。不得信任客户端直接提交的 open_id 作为身份证明，也不得将管理密钥放进 APK。客户端提交短期登录凭证，服务端验证后签发本游戏短期会话；日志不记录令牌。

## 数据模型和接口

| 数据 | 关键字段与约束 |
| --- | --- |
| players | player_id、provider、provider_subject；账号组合唯一 |
| profiles | player_id、schema_version、revision、天赋状态、updated_at |
| progress_events | player_id、event_id、类型、payload_hash、result_revision；账号内 event_id 唯一 |
| legacy_imports | player_id、import_id、快照摘要、导入时间；每账号最多一次初始迁移 |
| profile_history | 历次修订快照与保留期限；用于误覆盖恢复和审计 |

- `POST /v1/auth/taptap`：验证平台登录凭证，返回游戏会话。
- `GET /v1/profile`：返回是否存在云档、schema_version、revision 和进度。
- `POST /v1/profile/import`：仅在账号没有云档时导入旧版快照；重复请求返回同一结果。
- `POST /v1/profile/events`：提交事件批次及 base_revision；响应包含确认事件和最新权威快照。

每次状态变更在同一数据库事务中写入事件、更新余额和天赋、递增 revision。重复 event_id 且内容相同返回原结果；相同 ID 内容不同必须拒绝。客户端只在拿到明确确认后删除本地待同步事件。

## 旧版存档自动迁移

1. 覆盖升级保留现有 `user://saves/profile_01.json`，使用现有 backup 与 legacy 路径回退读取；迁移前另存一份不可被普通保存轮换掉的原始快照。
2. 完成隐私同意、账号登录与合规门禁后读取云档，查询成功之前禁止上传默认空白快照。
3. 云端明确不存在存档时，自动上传旧版天赋进度；服务端创建初始版本并记录 import_id。网络失败保留本地进度与迁移任务，重试同一 ID。
4. 云端已有存档且本机没有有效历史进度时，自动恢复云档，再开放天赋消费和开局。
5. 云端已有存档且本机有已确认的 revision 时，先补交本地待同步事件，然后使用服务端返回的新快照。
6. 未绑定的旧版本地进度碰到已有云档时，不能用余额较大者或时间较新者直接覆盖。保留本机快照，自动使用已有云档；记录冲突供客服恢复，必要时提供明确的异常处理入口。不得将两个余额相加。

迁移成功前不删除旧存档，成功后也保留迁移原始备份。已经卸载且没有其他备份的旧进度无法由这个功能补救。

## 结算和离线同步

本地持久化内容扩展为“进度快照＋待同步事件＋最后确认 revision”，作为一个提交单元保存。每局沿用唯一 run_id，结算事件使用稳定 event_id；死亡或撤退时先把奖励及事件落盘，再显示结算页面，不能等返回主菜单才登记。

本机写入失败时不显示已到账，保留可重试的结算状态；本机成功、上传失败时显示“本机已保存，联网后同步”。在结算、购买天赋、回到菜单和恢复联网时尝试上传，重试使用退避和抖动。切后台仅作额外机会，不能依赖退出回调才能保存。

云档启用后只提交结算、购买、重置等操作事件，不能每次用完整本地快照盲写覆盖云端。服务端按当前配置核验天赋费用与余额，保证不能因两台设备并发消费而出现负余额。过期的购买请求失败后回到最新权威状态并告知玩家；结算事件仍按 run_id 去重补发。

奖励事件去重只能防网络重试造成的重复发奖，不能证明客户端提交的战斗结果真实。当前游戏战斗在本地运行；首版至少验证字段范围、版本、合理奖励上限与速率并保留审计。强反作弊需要额外的可信战斗验证，不能声称云存档本身可以解决。

## 验证与上线顺序

先实现本地待同步事件和可注入的云存档客户端，再接后端认证与数据库事务，最后小范围开放迁移。服务端失败时继续保留本机档，禁止把失败或超时当作“云端无档”。账号切换必须隔离本地快照和待同步队列；上一账号的事件不能发给下一账号。

必须覆盖：88 点旧档和已购买天赋迁移；空档不能覆盖云档；重复提交不重复发奖；提交成功但响应丢失；结算写盘后强杀重启；断网购买后重连；双设备并发；切换账号；损坏存档；版本升级；迁移中断恢复；备份回滚。卸载重装验收使用独立测试账号和设备或隔离包，不能卸载玩家当前游戏作为测试。

验收标准：在线结算后确认云端已同步，卸载重装并登录同一账号，余额、已购买天赋及结算凭据一致；无需用户选择存档位置。

## 当前交付边界

文件夹选择方案已撤回；现有玩家存档行为保持不变。还需用户选择或提供云服务资源后才能部署可工作的云存档。隐私政策需更新实际使用的云存档服务、上传字段和数据删除方式。
